# Agent Guidelines — transcribe-ui

## Project overview

NiceGUI-based web frontend for Sunet Scribe (transcription service). Requires Python ≥ 3.13. Package manager: `uv` (see `uv.lock`).

## Architecture

- **Framework**: NiceGUI (Python-based web UI built on Quasar/Vue)
- **Entry point**: `main.py` — registers `@ui.page("/")` and `/logout`, handles OIDC auth callback and encryption-password bootstrap
- **Pages**: `pages/` — `home.py`, `admin/` (package, one module per admin page: `analytics.py`, `announcements.py`, `customers.py`, `groups.py`, `health.py`, `rules.py`, `shared.py`, `users.py`), `srt.py`, `user.py`, `status.py`. Each top-level page module exports a `create()` function called from `main.py`; `pages/admin/__init__.py` imports the admin submodules for their `@ui.page` side effects and re-exports `create` from `groups.py` for `/admin` itself.
- **Utilities**: `utils/` — split by concern:
  - `helpers.py` — `storage_encrypt`/`storage_decrypt` (AES-256-GCM), filename sanitisation, encryption-password set/verify/reset, customer/realm CRUD
  - `token.py` — `get_auth_header`, `token_refresh`, `get_user_info`, `get_admin_status`, `get_bofh_status`
  - `common.py` — `page_init()` and shared UI scaffolding
  - `settings.py` — pydantic `BaseSettings` loaded from `.env` via `get_settings()` (lru-cached)
  - `drive.py` / `drive_dialogs.py` — Get from / Save to Sunet Drive (see below)
  - `caption.py` (`SRTCaption`), `video.py`, `undo_redo.py`, `customer.py`, `group.py`, `crypto.py`, `styles.py`
  - `speech_timeline.py` / `speech_timeline.js` — the speech strip under the video (see below)
  - `recorder.py` / `recorder.js` / `recorder_reminder.js`, `recording_api.py`, plus `static/recorder_engine.js` — recording from the microphone (see "Recording" below)
  - The SRT/transcript editor is split across several files rather than one monolith — see "Editor split" below.
- **DB / analytics**: `db/analytics.py` — async `httpx` calls to backend API
- **Static assets**: `static/` — logos, favicon
- **Tests**: `tests/` — pytest with `nicegui.testing.user_plugin`; run with `uv run pytest` (or `.venv/bin/python -m pytest`)
- **Container**: `Dockerfile` at repo root

### Editor split (`utils/srt*.py`, `utils/transcript_editor.*`)

`pages/srt.py` opens one editor regardless of `data_format` — `TranscriptEditor` (`utils/transcript_editor.py`), a single `contenteditable` (Vue component `transcript_editor.js`) — backed by one `SRTEditor` (`utils/srt.py`) so saving, exporting, and word/review data work identically for both a transcription and a set of subtitles. `SRTEditor.render_override` points at `TranscriptEditor.refresh`, which is what `refresh_display()` calls; `SRTEditor.on_select` points at `TranscriptEditor.scroll_to`, which is what `select_caption()` (search, autoscroll) calls to bring a caption into view. The component takes a `subtitleMode` prop (`self.editor.data_format == "srt"`, set once in `TranscriptEditor.build()`) that swaps the speaker margin for a character-count guideline, one row per line (`caption_line_counts()`), each row lined up with its text line the same way the base rule lines the speaker up with the text. Those counts are redrawn as the caption is typed into, from the DOM text itself (`computeLineCounts()`, mirroring `caption_line_counts()` — same guideline, same tooltip wording, `characterLimit`/`maxSubtitleLines` sent down as props rather than duplicated as constants) into a `liveCounts` map keyed by block id, since `set_text()` deliberately does not re-render the block being typed into (it would move the caret) and so nothing else would keep the counts current; a real render (split/merge/undo) clears the map so the server's own answer takes back over — the margin is a column (`.transcript-subtitle-mode .transcript-gutter`, `flex-direction: column`) rather than the base rule's row, the caption's index heading it at the same height as the cell's timing row (`.transcript-subtitle-index`, a flex box of `height: 1.5rem` with the figure centred in it, matching `.transcript-action`'s own height — see below — rather than the shorter plain text beside it, since that is what actually decides the timing row's rendered height; centring rather than a tall `line-height` on a small figure, which half-leading pushed to the top of its box and read as the index sitting above the timestamp) with the per-line counts stacked below (`.transcript-subtitle-counts`), a `gap` matching `.transcript-subtitle-time`'s own `margin-bottom` keeping the first count aligned with the text's first line the same way the index lines up with the timing above it. The index names the caption itself, in the same column the counts are in but its own row, not folded into the first count row the way it once was. The timing itself sits in the cell, over the text it times rather than over the margin's counts, as two plain `<input>`s (`.transcript-time-input`) edited directly — no dialog, in either mode; a typed value is read back by `parse_time_label()` and applied via `retime()`/`apply_time()`, and a value that does not parse (or an end before the start) is refused and the input reverted, forced by marking the block dirty the same way a text edit does so Vue's own diff cannot skip a prop that ends up unchanged. A transcription's own `.transcript-time` uses the same input pair, just outside `.transcript-subtitle-content`'s flex wrapper (stacking the timing above the text, which only subtitleMode needs — a transcription's own `.transcript-time` and `.transcript-text` sit as plain siblings instead). subtitleMode also turns on per-caption split/merge/note/add/delete actions (`.transcript-cell-actions`), riding the same timing row rather than sitting beside the text below — quiet (opacity 0) until the caption is hovered or a reader tabs into one, still in flow so hidden it reserves its own width and height and the row does not reflow as they fade in and out. The row is a three-column grid (`1fr auto 1fr`) with the timing wrapped in `.transcript-subtitle-timing` as the first column and the actions as the middle one, which is what lands them on the row's *true* centre; equal auto margins on a flex item only centred them in whatever space the timing left over, noticeably right of centre, and the empty third column exists purely to balance the first (`splitAt()`, mouse equivalent of Ctrl/Cmd+Enter — prefers the caret when it is already in that caption, otherwise the middle of its text; merge reuses the existing `mergeblock`/`direction: "next"` event Delete-at-the-end already emits, no new server-side method) — a transcription has speakers and no length limit; a subtitle has the opposite. The music note (`insertNote()`, `♪` — a caption of song or of music under the picture is written with one, and no keyboard offers the character) is the one action in that row that is *not* structural: it is typed into the caption at the caret and carried to the server by the same `onInput()` a keystroke goes through, so it is marked as the reader's own and counted against the character guideline like any other character. A caret that is not in that caption means the note belongs to the caption as a whole rather than to a place in it, so one is written at each end — `♪ Lyrics ♪`, how a caption that is all music is written — the end first, since writing the opening note would move the end along and the length read before either insert is stale; an empty caption gets a single note rather than a pair with nothing between them. Both paths write through `writeNote()` and report through **one** `onInput()`, so the pair is one undo step. **The icon prevents the default on `mousedown`** — pressing the mouse down anywhere moves the caret, so without it the reader's own caret was already gone by the time the click arrived and every note landed at the end. `splitAt()` reads the caret the same way and carries the same guard. Structural edits (split/merge/add/delete/speaker/timing) are reported to the server rather than left to the browser, which owns the block structure and sends a fresh set back. `delete()` refocuses a neighbouring caption afterward (the one that took its place, or the new last one) the same way `add_after()` already focuses the caption it starts — refresh() removes the deleted caption's own DOM node, and a caret that was inside it does not survive that: left alone, the browser collapses the invalidated selection to the very start of the contenteditable, which reads as the cursor jumping to the top of the page. The same collapse hits a block that was typed into and never got a real render before one finally arrived (undo, most of all — see the revision watcher's own comment): changing that block's key so Vue rebuilds it rather than patches it, needed so undo's own text actually shows, throws away whatever element the caret was anchored to. The revision watcher reads the caret before that happens and, if it was in the block about to be rebuilt, restores it afterward with `placeCaretAt()` — the inverse of `caret()`'s own offset, walking the fresh (server-authoritative, so never carrying `plainText`'s placeholder) text nodes directly, falling back to the block's end if the caption shrank out from under it, and carrying the block's own change in length along with the offset before that — undo (most of all) changes the very text the offset was measured against, and restoring it unchanged into a block that shrank landed past the word the caret was actually at, into whatever now sat where the old, larger offset pointed. `merge()` refocuses the surviving caption at the seam between the two texts for the same reason `delete()` does — merging previous removes the very block the caret was in, and merging next is more useful landing exactly where the two met than wherever the caret already was — `focus()`/`focus_block()`/`focusBlock()` all now take an optional character offset (default 0, unchanged for `add_after()`'s own use) rather than always collapsing to a block's start, `focusBlock()` itself just handing that off to `placeCaretAt()`. `merge_with_previous()`/`merge_with_next()` only actually join the two texts with `"\n"` when both have something to separate — "Add caption after" followed straight away by Backspace merges the empty caption it just started back into its neighbour, and an unconditional join left that neighbour with a trailing blank line it was never typed into. `split()`'s own mid-text branch likewise refocuses the start of the new second block afterward, same as pressing Enter mid-sentence anywhere else — unlike a merge's removal the first block keeps its own DOM node here, so this is about landing where the reader expects rather than avoiding a broken caret; skipped when split_caption refuses the split (nothing on one side of the caret) since no second block exists to focus then. Enter means the same thing in both modes: **Enter starts a new caption** (a new block in a transcription) by splitting at the caret — at the end of a caption there is nothing to move across, so a new empty one is started instead — and **Shift+Enter inserts a literal line break** (`insertLineBreak()`, spliced in by hand — `document.execCommand("insertText", ..., "\n")` looked right but corrupted surrounding content in testing); a break landing at the true end of the caption's text also gets a trailing zero-width space, since a browser reserves no line box, and so no navigable caret, for a forced break with nothing real after it — `plainText()` strips that character back out wherever a block's text is read for anything other than drawing it (`caret()`, the edit reported to the server), so it never reaches the saved caption. Ctrl/Cmd+Enter splits as well, which is what it meant while Enter itself was the line break; nothing intercepts it, so it falls through to the same branch. **The Shift+Enter branch has to stay ahead of the split branch**, which only asks for Enter and would otherwise swallow it. **Paste is reduced to the clipboard's `text/plain` flavour** (`onPaste()`, with `@drop.prevent`/`@dragover.prevent` closing the drag route to the same HTML flavour): left alone, a contenteditable inserts the clipboard's *HTML* — markup chosen by whatever page the reader copied from, and an `<img onerror=…>` in it runs its handler on insertion, in this origin. The text is spliced in as a text node with the same Range technique `insertLineBreak()` uses (never `innerHTML`, never `execCommand`), gets that function's zero-width-space treatment for a trailing `\n`, hands a selection reaching into another block to the server instead (see below), and reports through the same hand-called `onInput()` — so a paste is marked, counted and flushed exactly as typing it would have been.

**A selection can reach across blocks, and no edit over one is left to the browser.** Nothing stops a reader dragging from the middle of one caption into another, and the gutters in between — the numbers, the speaker, the timings — are not editable text: a native Backspace over such a selection deletes those elements along with the text, and the editor comes apart on the page rather than losing the words it was asked to lose. `selectionSpan()` reports the two ends (`getRangeAt` gives them in document order, which is caption order, however the drag went) and `onKeydown` intercepts every key that would edit over one — Backspace, Delete, Enter, and any printable key, which is sent along as the replacement text the way the paste is — plus `onCut()` and `onPaste()`, all emitting **one** `deleterange`. `onCut()` fills the clipboard by hand first, since preventing the default prevents the copy half of a cut too, and builds that text from the blocks' own text (`spanText()`) rather than `selection.toString()`, which sweeps the gutters in with it. `TranscriptEditor.delete_range()` → `SRTEditor.delete_range()` does the whole gesture as one edit and so **one undo step**: the first caption keeps what lies before the selection, the last keeps what lies after, the two become one caption spanning both timings, and the captions between them go. Edit marks are carried by joining every touched caption's marks as if their texts had already been merged (`joined_edits`) and retagging that against what is left (`retag_edits`), so both surviving halves keep their marks and whatever was typed or pasted in earns marks of its own. It returns the seam's offset, which `delete_range()` hands to `focus()` — the blocks the selection ended in are gone from the DOM, and a caret left inside one does not survive the render (the same reason `merge()` and `delete()` refocus). Enter deliberately does **not** also split at the seam: one gesture, one edit, one undo step, and a second Enter there splits as it always does. `block_id()` takes a key name for this event's two ids. The timing rows (`.transcript-time`, `.transcript-subtitle-time`) are `user-select: none` — the gutter already was — so a selection dragged across captions paints only the words it will actually take; the inputs opt back in **on focus only** (`.transcript-time-input:focus`) — a document selection that merely encloses an input still paints that input's own value as selected, so an unconditional `user-select: text` there was itself what kept the timestamps highlighted; focus is enough for editing, since a click focuses the field on mousedown before any drag inside it starts. Covered by `tests/test_delete_range.py` and `TestTimingIsNotText` in `tests/test_caption_editor_styles.py`.

A caption is a paragraph on a page, not a filled cell: giving each one a fill of its own was tried and turned down. `.transcript-text` does set `cursor: text` — the pointer stayed an arrow over the whole editor before, which was the clearest thing saying it was not one. Note that any vertical padding on `.transcript-cell` has to be matched on `.transcript-gutter`: the two are separate items on the same grid row, not parent and child, so padding one alone slides the index and character counts out from under the lines they belong to.

The caption the caret is in marks itself too (`caretId` in the component, `.transcript-cell-editing`), read from the selection in `updateCaretBlock()` on keyup, click, input and `focusBlock()` rather than tracked through edits — the caret moves for reasons nothing in the component hears about. It is deliberately separate from `activeId`, the caption being *played*: the reader is very often editing one caption while listening to another, and `.transcript-cell-editing` is stated after `.transcript-cell-active` so the caret wins the background when both are true. `@blur` now runs `onBlur()`, which flushes exactly as it did and clears the marking with it.

- `srt.py` — `SRTEditor` core: state, caption CRUD, undo/redo wiring (delegates to `undo_redo.py`), `parse_srt`/`parse_txt`.
- `srt_render.py` — validation and the keyboard-shortcuts dialog. **Validate opens the docked validation panel under the video, below the settings ("Uncertain words" last)** (`utils/validation_panel.py`, SUNET/scribe-ui#138), not the dialog: one issue at a time from `validation_items()` (issues, not captions — a caption with two problems comes up twice), each with a heading naming the rule, a detail and "Caption N" as a button that puts the caret where the problem is. Previous/Next are relabelled, never rebuilt, so focus stays put; at either end focus hops to the other button before the one that went too far is disabled. Each step calls `TranscriptEditor.review()` (the component's `reviewId`, `.transcript-cell-reviewing`), not `select_caption()`, which toggles. Closing keeps the captions' invalid markings and returns focus to Validate. Checkboxes below the panel (one per kind found, "Overlaps (2)", only when there is more than one kind, or a kind found is hidden -- `filters_wanted()`; hiding a kind and fixing the rest otherwise left it hidden with no checkbox to bring it back) hide or show kinds of issue: every item carries a `rule` (`RULE_LABELS` in `validation_panel.py`), hidden kinds are kept across Validate runs, and the issue on screen stays put if its kind is still shown. **A marked caption never refuses to open its card because of a filter** (`reveal_hidden()`, from `follow_caret()`): the marks in the text are for every issue whatever is filtered, so when the caret comes to rest in a caption whose issues are all of hidden kinds, the kind of its first issue is shown again (its checkbox comes back ticked, `draw_filters()`) and that issue opens, with a line on the card and the same said to a screen reader ("Showing \u201cOverlaps\u201d again \u2014 it was hidden." -- through `pending_speech` and `speak()` when the panel had only just opened, since a live region that appears with its text is often not read). A caption that has an issue of a kind that is shown opens on that and its other kinds stay hidden, which is what the reader chose; speech without a caption marks nothing and never brings a kind back. This is what lets a reader hide everything but one kind, fix those, close the panel and still find every other flagged block later. `set_shown()` only acts when a checkbox disagrees with what is shown, so it can never toggle twice. "Check again" under the issue (`check_again()`, via `SRTEditor.revalidate_items()` / `run_validation()`, shared with Validate) re-checks every caption -- a timing fix changes its neighbours' overlaps too -- then stays on that caption's first remaining issue, or moves to the next issue after it, and says which ("Caption 17 passes now."). The dialog (`show_validation_report`) remains only for a page without the panel. Every issue is said in words ("Error:"/"Warning:" plus the rule), the icon and colour only repeat it. No longer draws anything itself — see above. `collect_validation_issues()` is the check itself, separate from the dialog that reports it (`show_validation_report`) and tested on its own in `tests/test_validation.py`: one entry per caption carrying everything found in it, in caption order, split into **errors** (no text, ends before it starts, same timing as an earlier caption, overlaps a neighbour) and **warnings** — the subtitle guidelines, so subtitles only: line length against `CHARACTER_LIMIT`, line count against `MAX_SUBTITLE_LINES`, time on screen against `MIN_CAPTION_SECONDS`, and speech no caption covers for longer than `MAX_UNCAPTIONED_SPEECH_SECONDS` (`uncaptioned_speech()`, from `speech_runs()` cut at every caption, so a caption deleted from the middle of one long run still shows; filed under the caption the speech follows with `mark=False`, since that caption is not itself wrong, and carrying `speech` {start, end, until} for the panel's "Add caption", which goes through `TranscriptEditor.create_caption()` like a drag on the strip, sized by `new_caption_span()`). It sets `is_valid` (and `has_error`) as it goes, so the editor's own left rule and the report can never disagree — the caption's highest severity decides: red if any of its issues is an error, amber (`.transcript-cell-warning`, the panel's `--color-warning-border`) for warnings only — the review outline too, whichever of its issues the panel is on. Every caption in the report is a row that jumps to it (`select_caption`), since finding "#47" by scrolling was the one thing the report left the reader to do.
- `srt_review.py` — word-level review/edit marking shared by both formats (`retag_edits`, `review_runs`, confidence flagging).
- `srt_search.py`, `srt_export.py` — search panel and export dialog, shared by both formats.
- `transcript_editor.py` / `transcript_editor.js` — the editor itself, described above.

**Gotcha with `transcript_editor.js`:** NiceGUI registers a custom Vue component (`component="…js"`) once, at class-definition/import time, keyed by file content — a running server keeps serving the old JS until the *process* restarts, not just the browser. `ui.run(reload=True)` is on by default, but uvicorn's reload watcher only globs `*.py` by default, so an edit to this file was silently invisible to a running dev server. `main.py` now passes `uvicorn_reload_includes="*.py, *.js, *.vue"` so edits here trigger the same auto-reload `.py` changes do — if a JS fix still doesn't seem to apply, restart the server by hand and confirm that setting is intact.

## Key conventions

- All authenticated page handlers must call `page_init()` before accessing secret storage keys. `page_init` redirects to `/` when `_scribe_bk` missing in browser storage and refreshes the OIDC token.
- All API calls MUST be async — use `httpx.AsyncClient` (see `db/analytics.py`). Do not introduce blocking `requests` or sync `httpx` calls in new code; legacy sync calls in `utils/helpers.py` should be migrated when touched.
- API calls use `get_auth_header()` from `utils/token.py` for bearer-token auth.
- NiceGUI `ui.table` uses Quasar slot templates with `$parent.$emit('event_name', props.row)` for per-row actions.
- Dialog close on validation failure uses short-circuit pattern: `result and (dialog.close(), navigate)`.
- Use `match/case` statements (Python 3.13+).
- **A toast that has focus gives it back when it goes.** A toast with a Close button takes focus when it is pressed (or tabbed to) and drops it to `<body>` when it leaves, so the next Tab would start at the top of the page. The script at the bottom of `default_styles` (`_scribeToastFocus`, `utils/styles.py`) remembers the last focused element that is not a toast and focuses it again when a toast that held focus is removed — only if that element is still connected and has a box, and never when focus is on something real by then. It watches only Quasar's `.q-notifications` container, not the page. New toasts need nothing; do not add focus calls of your own after `ui.notify`.

## Security

This app holds session tokens, user PII, and an encryption password that gates backend-side data encryption. Treat security as a first-class concern in every change.

### Authentication & session

- Authentication is OIDC. The flow lives in `main.py` (`@ui.page("/")` and `/logout`).
- **The landing page collects the login's tokens with a one-time code, not from the URL.** The backend's OIDC callback redirects to `/?code=…`; `exchange_login_code()` (`utils/token.py`) posts that code to `OIDC_APP_EXCHANGE_ROUTE` and gets `{"token", "refresh_token"}` back server to server, so the tokens never travel through the browser. They used to arrive as `?token=…&refresh_token=…`, which left a working set of credentials in history, in referrers and in every access log on the way. The code is single-use and lives about a minute; the page spends it and clears it out of the address bar with `history.replaceState`. A refused code, and the backend's own `?error=login_failed`, both end as a notification and no session. `OIDC_APP_EXCHANGE_ROUTE` is a new setting — without it nobody can log in.
- Every authenticated page handler MUST call `utils.common.page_init()` first. It:
  - redirects to `/` if `app.storage.browser["_scribe_bk"]` (browser key) is missing,
  - schedules `token_refresh()` on each page load and logs out on refresh failure by clearing `token`, `refresh_token`, and `encryption_password` from `app.storage.user`, then navigating to `OIDC_APP_LOGOUT_ROUTE`.
- Never read `app.storage.user["token"]` / `["encryption_password"]` without going through `page_init()` first.
- Authorization checks: `get_admin_status()`, `get_bofh_status()`, `get_user_status()` in `utils/token.py`. Admin pages must gate on these — do not infer privilege from UI state.

### Secret handling

- Browser-bound encryption: `storage_encrypt` / `storage_decrypt` in `utils/helpers.py` wrap `utils/crypto.py` (`AESGCM` + `HKDF` from `cryptography.hazmat`, base64-encoded ciphertext, random 12-byte nonce, AAD `b"scribe-secret"`).
- Key material = `app.storage.browser["_scribe_bk"]` ++ `settings.STORAGE_SECRET`. Salt = `get_browser_id()`. Never log, print, or echo any of these into UI text, error messages, or exceptions.
- Decryption failure intentionally clears `encryption_password` and redirects to `/` — preserve this fail-closed behavior; do not catch and continue.
- Any new value stored in `app.storage.user` that contains tokens, passwords, keys, or PII MUST go through `storage_encrypt`.
- `STORAGE_SECRET` default in `utils/settings.py` is a placeholder. Production deployments must override via `.env`. Never commit a real secret.

### Input handling

- Filenames coming from users or the API: pass through `sanitize_filename()` (strips `/ \ \x00 < > : " | ? *` and control chars, trims `. ` ).
- Any text rendered into NiceGUI: prefer `ui.label`/`ui.markdown` — avoid `ui.html` with untrusted input. If raw HTML is unavoidable, sanitise with a library like Bleach (`bleach.clean`) rather than ad-hoc regex.
- Validate at boundaries: API responses and form input. Internal helpers can trust their callers.
- Logs must use `user_id`, never usernames, email addresses, or other PII.

### Crypto rules

- Use the existing `utils/crypto.py` helpers. Do not roll new AES/HKDF code; do not switch to ECB, CBC-without-MAC, or PyCryptodome.
- Prefer the secure-by-default `cryptography` package (already a dep). For new crypto needs, evaluate Google Tink before bespoke code.
- Never hard-code keys, IVs, or salts. Nonces must be `os.urandom(12)` per encrypt call (already done by `encrypt_string`).

### Transport & external calls

- All outbound HTTP MUST use `httpx.AsyncClient` (see `db/analytics.py`). Set explicit timeouts. Do not disable TLS verification.
- Backend base URL comes from `settings.API_URL`. Do not concatenate user input into URLs; pass via `params=` so `httpx` quotes them.
- SSRF: if a feature ever fetches a user-supplied URL, block private/loopback ranges before connecting (e.g., an SSRF filter library) — there is no such code path today; flag any addition for review.

### Container & deps

- `Dockerfile` should not run as root in production; pin base image and pip-installed versions.
- Dependencies are tracked in `pyproject.toml` / `uv.lock`. Run `uv lock --upgrade` deliberately, review the diff, and prefer libraries from the "secure-by-default" list (Bleach, defusedxml, Tink) over hand-rolled equivalents.

## Word timings (`utils/srt_review.py`)

`SRTEditor` is `ReviewMixin, SearchMixin, ExportMixin, RenderMixin` composed onto the core defined in `utils/srt.py` (see "Editor split" above). `ReviewMixin.load_words()` takes the optional payload from `GET /api/v1/transcriber/{uuid}/words`:

```json
{"version": 1, "words": [{"t": "Hej", "s": 0.12, "e": 0.34, "c": 0.98}]}
```

- Anything with a different `version`, or an unparseable payload, is discarded — the editor must open normally without word data. Jobs transcribed before word timings existed have none.
- Words are flat and time-ordered, not tied to segments. `caption_words()` maps them onto a caption by time range (bisect on precomputed midpoints), so they survive splits, merges and renumbering. Never key word data by caption index.
- `split_caption(caption, cursor_position=..., text=...)` cuts at the caret and picks the timestamp from the silence between the two adjacent words. Without word data a caret split falls back to proportional; **a split with no caret must keep halving the caption**, which is what results predating this feature rely on — and that halving goes through `split_point()`, which takes the gap between words nearest the middle, looking **both** ways. Searching backwards only and settling for the bare middle when nothing was found cut straight through the first word of any caption with no space before its midpoint. A caption of one long word has no gap and keeps the middle; every real caption has one.

A position the reader actually chose is honoured to the character, mid-word or not — only made-up ones get snapped, which is why `splitAt()` sends **no offset at all** when the caret is not in the caption it was clicked on, rather than the middle of the text dressed up as a caret. `TranscriptEditor.split()` treats a missing offset as "halve this"; note it checks `offset is None` rather than falsiness, since `0` is a real caret position (at the very start, where the split is refused for having nothing on one side).
- `c` is absent when the worker ran with `WORD_CONFIDENCE=false`. Gate the review controls on `editor.has_confidence`, not on the presence of `words`.
- The editor renders review/edit marking as structured runs (`review_runs()`, one dict per run: `t`/`flag`/`edit`/`s`/`e`), consumed directly by `transcript_editor.js`'s Vue template rather than as an HTML string — never build caption markup inline. `get_review_html()`/`review_backdrop_html()` produce the same marking as escaped HTML for callers outside the live editor (e.g. tests asserting on the marking itself); nothing in the UI renders them today.
- Live edit marking (the `[data-changed]` attribute `onInput` sets, styled green only under `.transcript-show-edits` — see `TranscriptBody.set_show_edits`, and `build()` syncing it from `editor.show_my_edits` before the first render, since that toggle is a saved preference and can already be on when the page loads) is a client-side stand-in for `review_runs()`'s own `edit` flag, needed because `set_text()` deliberately never re-renders the block being typed into. `spaceAtTail()` stops a space typed at a word's own tail from marking that word — the browser extends the same span for it, "nowhere else for it to go" — but the next *real* character removes that trailing whitespace, so `effectiveSpan()` remembers the crossing as `newWordBoundary` (a span+offset pair, forgotten if the caret ever dips back below it — editing the original word again) and, the moment real content exists past it, calls `splitNewWord()` to move that content into a new sibling span of its own before marking it — marking the original (shared) span would mark the old word too. A second space typed right after the first extends the boundary instead of splitting: there is still nothing but whitespace past it, so nothing to give a span of its own. The one place this reaches into the DOM directly rather than only reading it; safe because `dirty` already guarantees whatever shape it leaves gets discarded and rebuilt at the next real render regardless. `markChanged()` itself refuses to mark a span of pure whitespace no matter which path hands it one — `wordAt`/`effectiveSpan` both work at DOM element boundaries, not word boundaries, so a caret can legitimately land inside a separator's own span, and there is no word there to highlight. The mirror case — typing a new word in *before* an existing one, caret at the boundary between a separator and the word right after it — resolves into the separator's own tail too, the same way `spaceAtTail` exploits for the word-before-a-space case, but nothing here remembers a boundary across keystrokes the way `newWordBoundary` does, since the whitespace prefix never changes: `effectiveSpan()`'s `headMatch` branch (`/^(\s+)(\S+)$/` against the span, caret at its tail) fires and calls `splitNewWord()` on the very first real character, isolating the new word immediately rather than waiting for a second keystroke to cross anything. Splitting alone still leaves the new word flush against the one after it with nothing between them in the DOM — fine while the reader keeps typing, since nothing has been sent yet, but the debounced `flush()` 400ms out does not know that, and a natural pause mid-word sends the two run together (`"thereworld"`) as an undo-able state, with `retag_edits()` then correctly, if unhelpfully, marking that merged token as edited once undo lands on it. A synthetic space (a bare `Text` node, `this.syntheticSpace`) is appended right after the new word's span the same moment it is split off, so every flush from there on stays properly spaced even before the reader finishes typing a separator of their own; `spaceAtTail()` firing against that same span — the reader's own trailing space — retires it, so a real one and the synthetic one already standing in for it never both persist. `retireSyntheticSpace()`, called at the top of `onInput` before the caret or the text are read, covers the other way that space stops being needed: the reader backspacing the new word away again. `spaceAtTail`'s own retirement cannot catch that — it only fires when a real space is typed — and left in the DOM the space is read straight back out as part of the caption, flushing a stray double space the reader never typed as its own undo-able state (and, in subtitleMode, counting against the character guideline). "No longer needed" is everything ahead of it inside its own parent being whitespace: the new word had a span of its own, and the browser takes that span away with the last character of it.

### Words flagged for review

One control, **Off / Low / Medium / High**, highlights words the model was least sure of and picks how far up the confidence range to flag, via `REVIEW_SENSITIVITY_*` in settings. Raising the level must only ever flag more.

There was a separate "Uncertain words" switch alongside a Low/Medium/High selector; "off" is simply the lowest setting of the same thing, and splitting them meant two places to look to find out whether anything was being flagged at all. The model underneath is unchanged — `show_uncertain_words` (bool) plus `review_sensitivity` — and the control writes both: "off" sets the flag false and **leaves the stored level alone**, so coming back lands where the reader left it, and `REVIEW_SENSITIVITY_KEY` is never written the string `"off"` (it is not one of `REVIEW_SENSITIVITIES`, so `set_review_sensitivity` would reject it anyway). The selector is the only review-coloured control now, so `.q-toggle.review-switch` is gone and only `.bg-review-accent` carries `--color-review-accent`.

- **Every flagged word is marked identically** — one class, one shared tooltip. The score is not a calibrated probability, so it cannot support grading flagged words against each other, and the raw number is never shown anywhere.
- **The marking must not read as an error.** No red, and no wavy underline (that means spellcheck). It uses `--color-review-*`, a violet reserved for this and used nowhere else.
- The flagged counter comes from `flagged_word_count()` over the whole word list, and reports 0 while the switch is off. Anything that changes the switch or the sensitivity must call `update_flagged_count()`.

### Highlights (SUNET/scribe-ui#131)

The reader's own highlighter: a note to self made while reviewing against the recording, never a change to the text. Stored as `SRTCaption.highlighted_words`, word positions counted exactly as `edited_words` is, and **kept apart from it** -- the two mean different things and move differently when the text does. Anchored to whole words, not characters: a selection that takes any of a word takes all of it (`words_in_selection()`; nothing selected means the word the caret is in or against), so a highlight survives every edit the way an edit mark does, and cannot end up cutting a word.

- **They follow the words.** `carry_highlights(previous, current, marked)` is the highlight's own `retag_edits`: words that stay move with their marks, words replaced one for one keep the mark, a longer or shorter replacement is highlighted when everything it replaced was, words typed *between two highlighted words* join the highlight and words typed anywhere else do **not** earn one (unlike an edit mark: typing a word is not highlighting it), removed words take theirs with them. `carry_marks(caption, new_text)` does both kinds in one call and is what every site that replaces a caption's text goes through (typing, split with unsent text, Find & Replace). Split/merge/`delete_range` reuse `split_edits`/`joined_edits` on the second set, and the one-word moves carry it across (they still do not carry edit marks). Any new place that rewrites `caption.text` has to carry both sets.
- **Toggling.** Ctrl+Shift+H (Ctrl only, by `event.code === "KeyH"`: Cmd+Shift+H is the browser's Home on a Mac; no Alt) reports `togglehighlight` with one `{id, start, end}` per block the selection reaches into (`highlightSpans()`, offsets in each block's own text), ahead of the block-scoped lists because those see only the caret's block. `SRTEditor.toggle_highlight()` takes everything touched: all already highlighted -> remove, otherwise add (a mixed selection becomes fully highlighted, a second press clears it). One undo step. `TranscriptEditor.toggle_highlight()` redraws and **puts the selection back** (`selectRange()`, offsets are unchanged because the text is), so the same key undoes what it did. Nothing selected and no word at the caret says so. **The toolbar's Highlight button** (`pages/srt.py`, where Validate sits in the subtitle editor, so transcriptions only) does the same for whoever does not know the key: it calls `TranscriptEditor.highlight_selection()` -> the component's `highlightSelection()`, which reads the selection as it is and emits the same `togglehighlight` (an empty list when nothing is selected, answered with the notice). It prevents the default on `mousedown`, as the caption row's note icon does, so pressing it does not take focus and the selection with it; `aria-keyshortcuts` names the key, the tooltip too.
- **Saved with the transcription -- and for now only there.** `to_dict()` writes `"highlighted"` (only when non-empty) next to `"edited"` and `parse_txt()` reads it back, ignoring anything that is not a list of ints. A set of subtitles is saved as plain SRT, which has no room for it, so **highlights are a transcription feature for now**: the key is not bound in `subtitleMode`, `SRTEditor.toggle_highlight()` refuses for `data_format == "srt"`, the shortcuts dialog has no "Highlighting" group there, and neither export option is offered or applied (`export_rtf()` ignores both for subtitles). The way to extend it is a place to keep marks beside an SRT result (positions plus a digest of each caption's text, restored only onto a caption with the same number and text) -- a backend endpoint; a working draft exists on the local branch `backup/highlight-words-with-subtitle-marks`, never pushed.
- **Drawing.** `review_runs()` gives a highlighted word `hl: true` (and makes every word a run of its own whenever a block has any highlight, while they are shown (see the switch below)); the space between two highlighted words is a highlighted run too, so a passage reads as one stretch, except across a line break. The component draws `runClass(run)` (the review/edit class **and** `highlight-word`) with `role="mark"`. Yellow, and a 2px line above and below: yellow on white is 1.14:1 so colour cannot carry it (1.4.1/1.4.11) -- the lines are 4.9:1 against the page in light mode and the text on the yellow 13.6:1; dark mode uses a dark gold (8.0:1 text, 12.6:1 frame). No horizontal padding, so highlighting does not move the text. On a flagged or changed word the highlight keeps its frame (line above and below, as on any highlight) and the word's own bar is drawn outside it, 3px below (`box-shadow` with no inset, so no room is taken): the bar once took the frame's lower line, which made a flagged highlight look like a flagged word on a yellow wash. The playing word's tint wins the wash and the lines stay.
- **RTF export** (`export_rtf(..., highlights=False, edits=False)`, the two checkboxes in the export dialog, transcriptions only, **off by default** and **hidden when there is no mark of that kind** to carry, `rtf_marks_available()`, across every transcription of a bulk export): highlights as `\highlight1` (pure yellow, Word's own marker colour), changed words teal and underlined (`\cf2\ul`, underlined because a printout may have no colour). `marked_spans()` splits a caption into whole-word pieces; the same bridging rule as the editor. The colour table is only written when used, so a clean export is byte-for-byte what it was. No other format carries either.
- **A word typed between two highlighted words is drawn highlighted at once, not only after the next render.** `carry_highlights` marks it on the server, but `set_text` does not re-render the block being typed into, so `highlightNewWord()` (called from `splitNewWord()` only, i.e. for a *new* word, and only when the nearest word on each side is highlighted) puts `data-highlighted` and `role=mark` on its span, styled by `.transcript-text span[data-highlighted]`; the next render drops both, like `data-changed`. Anything that changes which words `carry_highlights` marks has to change that rule too.
- **A switch hides them (Highlights, beside My edits, transcriptions only).** **Not saved**: every editor opens with them shown, and hiding them lasts until the page is left or reloaded -- it is a way of looking at the text for a while, not a preference, and a hidden highlight forgotten for days is worse than switching them off again (there is deliberately no storage key and no count on the switch); `set_show_highlights` re-renders. Hidden means **not drawn and not read out**: `review_runs()` is given no highlights at all, so no run carries `hl`, nothing is a `role="mark"`, and `highlightNewWord` has no highlighted neighbour to copy -- the component needs no flag of its own, and hiding is not CSS. The data stays: `highlighted_words` still follows every split, merge, move and edit, silently, and is still saved. **What cannot be seen is never taken away**: with them hidden, the command (`toggle_highlight` -> `reveal_highlights`) *never removes* -- it adds a highlight to any selected word lacking one, turns the display on (moving the switch through `editor.on_highlights_shown`, which the page sets; the page's handler skips the redraw when the command already did it), and says why with a toast that stays until closed (Quasar gives a toast `role="alert"`, so it is announced -- no separate status region, which would read it twice): "Highlights were hidden and are shown again. Press again to remove this highlight." (all already highlighted: nothing changed, so not a change to save and not an undo step), "Highlight added. Highlights were hidden and are shown again.", or "...and the words without one were highlighted." for a mixed selection. The next press, with them showing, removes as before. Nothing is said while they are shown. The RTF checkbox "Include highlights" is independent of the switch, and undo/redo still changes highlights that are hidden.
- Tests: `tests/test_highlights.py`, `tests/test_highlight_visibility.py`.

### Comments (SUNET/scribe-ui#131, the second half)

A note on a stretch of words, with a text of its own: `SRTCaption.comments`, a list of `WordComment(words, text)` (`utils/caption.py`), the words counted exactly as the highlight's are. **Stacked on the highlights branch**, and it reuses its rules: `CommentsMixin` (`utils/srt_comments.py`) carries each comment's words with `carry_highlights()` -- so the two kinds of note cannot drift apart -- and `carry_marks()` carries comments too, which covers typing, split with unsent text and Find & Replace. Split divides the list (`split_comments`; a comment across the split is on both halves with the same text, as separate copies), merge and `delete_range` join it (`join_comments`; neighbouring comments stay separate notes), and the one-word moves (`move_first_word_to_previous`, `move_last_word_to_next`) divide and join it with the same two helpers: **a comment stays on its word wherever the word goes**, so one on the moved word alone goes with it, and one on that word and others is on both sides (a copy with the same text). A comment with no words left is gone, with its words. Any new place that rewrites `caption.text` has to go through `carry_marks`.

- **Rules.** A comment belongs to **one caption**: a selection reaching across blocks is refused with a notice (a selection that merely brushes the edge of the next block is not across). A word has **at most one comment**: asking to comment on words that already have one opens that comment (`comment_target()`), never a second over it, so no drawing, navigation or export has to deal with overlap; `restore_comments()` enforces it on read too. Text is stripped, never empty (Save is disabled, `set_comment()` returns "" for it) and at most `COMMENT_MAX_LENGTH` (1000) characters. Transcriptions only for now: the key is not bound in `subtitleMode`, there is no panel for `data_format == "srt"`, `set_comment`/`remove_comment` refuse, the dialog group is absent and the export option is not offered -- the same reason as highlights (SRT has nowhere to keep it).
- **Saved** as `"comments": [{"words": [...], "text": "..."}]` per segment, only when there are any. `restore_comments(saved, text)` ignores anything unusable (junk shapes, empty text, non-int or bool or negative or out-of-range positions, a word already taken by an earlier comment) and cuts an over-long text.
- **The panel** (`utils/comments_panel.py`, `CommentsPanel`) is where a comment is written, read and changed. It is a card in the right column under the video, built like `ValidationPanel` (same `validation-panel*` classes, `.is-comment` sets `--vp-tone` to the comment colour): a head with Previous / position / Next and Close, then the words (a button that goes to them), where they are (`where_text()`: the speaker and the start time, as the editor shows them beside the text -- **not a paragraph number, which a transcription does not show**), a text area and Remove / Cancel / Save. **One comment at a time**, shut until needed. `pages/srt.py` builds it for transcriptions only (`transcript.comments_panel`), and `TranscriptEditor.refresh()` ends with `comments_panel.sync()` so a comment that an edit or an undo replaced is found again and one that is gone hides the card. **`sync()` draws the card again every time** (`draw(scroll=False)`; the text box is left alone, so what is being typed is kept), because the speaker and the time it shows come from the caption: a renamed speaker has to show. `TranscriptEditor.set_text()` calls it too, since the block being typed into is not rendered again and no `refresh()` follows: without it a comment whose words were all deleted stayed on the card. A comment is found again by `find_again()`: first by the same words (an undo puts back a copy), then, because an edit builds *new* `WordComment`s with moved words, by the same text and the most words in common.
- **The panel's Remove and Cancel are flat buttons and take `--color-brand-primary` for their text in light mode.** Quasar's own primary blue (#5898d4) is 3.06:1 on the card's white, under the 4.5:1 that 14px text needs (WCAG 1.4.3); dark mode needs nothing, the global flat-button rule draws them white.
- **Opening it.** Ctrl+Shift+K (Ctrl only, by `event.code === "KeyK"`, no Alt/Meta) or the toolbar's **Comment** button (`sym_o_add_comment`, beside Highlight, `mousedown` prevented so the selection survives) -> `commentSelection()` -> `opencomment {spans}` -> `TranscriptEditor.open_comment()` -> `CommentsPanel.open_for()`, which shows the existing comment on those words or an empty card for a new one, with focus in the text area. A file that has comments opens with the first one on the card (`open_first()`, no focus, text not moved).
- **The caret drives the card** (the same idea as the validation cards). The component reports `caretcomment {id, cm, click}` **once per comment** when the caret enters one (`reportCommentCaret()`, called from `updateCaretBlock()` and from `onClick` with `click: true`), and `CommentsPanel.follow()` shows it. An open card follows the caret; a **shut** card opens only for a *click*, so an arrow key crossing commented words does not throw a card up under someone typing; the comment already shown is left alone. A selection that is not collapsed reports nothing (a drag to copy words does not open it).
- **Marking where the card is, in the text.** `CommentsPanel.mark()` (called from `draw()` and from `sync()`, cleared by `hide()`) tells the component, through `TranscriptEditor.mark_comment()` and the props `commentId` / `commentIndex`, which caption and which comment the card is on. The caption gets `.transcript-cell-commenting` (a 3px rule and a 2px outline in the comment colour, like the validation panel's `-reviewing`, after the editing/invalid rules so it wins) and the words of the comment get a `data-comment-current` attribute (`isCommentOnShow()`), drawn as an 18% tint of the comment colour in a `background-image`, which paints above `background-color`, so a highlight's, flagged or changed word's own wash shows through. An attribute and not a class so `runClass()` is untouched. A comment being written marks its caption only. Previous/Next also scroll the caption to the middle (`scroll_to_block`) without moving the caret or taking focus, so the buttons can be pressed again. Contrast: text at least 6.7:1 (light) / 5.9:1 (dark) on the tint over every wash, the comment line at least 4.3:1 / 3.4:1; pinned in tests.
- **What is typed is kept when the reader moves on** (`commit()`): to another comment, into the text, with Previous/Next, or shutting the card -- if it is non-empty and different from what was there. Escape (in the text area) and Cancel are the ways to abandon; Ctrl/Cmd+Enter and Save keep it. Previous/Next are disabled while a new comment is pending. **Keys typed in the text area do not reach the page** (a `keydown` handler with `stopPropagation`; NiceGUI's `ui.keyboard(ignore=[])` is global and listens on the document, so otherwise Ctrl+Z would undo the transcript while a sentence is being written and Ctrl+S would save). After Save, Cancel and Remove the selection goes back on the words (`select_words`). A `sr-only` live label (`spoken`) says "Comment 2 of 5" and the like.
- **Drawing.** `review_runs()` gives a commented word `cm` (the comment's index in the caption); the first word also `cf` and `ct` (the text), the last `cl`. The space between two words of the same comment is in it (not across a line break, not between two comments). A word is drawn with `comment-word`: a **dotted 3px underline, 4px below the text**, in `--color-comment-line` (`#a1136a` light, `#ff9fd2` dark: 6.3-9.4:1 on every wash a word can have, except 4.6:1 on the dark highlight, all above 3:1). A pattern and not colour alone (1.4.1), drawn with `text-decoration` so it takes no room, touches no box-shadow (the other markings keep theirs) and needs no `::after` -- which the review/edit words already use for a hover message that the editor turns off to protect the caret, and a marker after the last word would sit where the caret goes. It is thick and offset because a thin line close to the text was lost against the highlight's own frame lines on words that are both highlighted and commented (rendered in Chromium, both themes, wrapped and not). The comment colour is magenta, not blue: blue is the progress/playing tint. The first word has `aria-description="Comment: <text>"`; **not tested with a screen reader**.
- **RTF export** (`export_rtf(..., comments=False)`, an "Include comments" checkbox, **off by default and hidden when there is none**, `rtf_comments_available()`, bulk exports included): each comment is written as a Word comment -- `{\*\atrfstart N}` before its words, `{\*\atrfend N}{\*\atnid SC}{\*\atnauthor Scribe}\chatn{\*\annotation{\*\atnref N}{\*\atndate D}\pard\plain\f0\fs20 text}` after (`rtf_date()` packs the date as RTF wants it). The pieces of `marked_spans()` are cut where a comment begins or ends so a marker never lands inside a piece; the text between the markers is the caption's own text throughout. Author is the constant "Scribe", **on purpose**: the username is available (`utils/token.get_user_info()`), but it would put a personal identifier into every exported file, and nobody else can write or export a user's comments (files are not shared between users), so there is no one to tell apart. Do not add it without deciding that again. Checked by converting an export with LibreOffice and by opening it in Word (comments by "Scribe" with the right ranges). Highlights show in the export only with "Include highlights" ticked, which is separate. A clean export is byte-for-byte unchanged.
- **A switch hides them (Comments, beside My edits, transcriptions only).** **Not saved**: every editor opens with them shown, and hiding them lasts until the page is left or reloaded -- it is a way of looking at the text for a while, not a preference, and a hidden comment forgotten for days is worse than switching them off again (there is deliberately no storage key and no count on the switch); `TranscriptEditor.set_show_comments` re-renders. Hidden means **not drawn and not read out**: `review_runs()` gives no run `cm`/`cf`/`ct`/`cl`, so nothing carries `data-comment` or an `aria-description`, and the caret has no commented word to report (`caretcomment` never comes; `CommentsPanel.follow` and `open_first` also refuse while hidden). The comments stay on their words in the data, follow every split, merge, move and edit silently, and are still saved. **Hiding puts the card away** (`CommentsPanel.put_away()`: `commit()` first, so nothing typed is lost, then `hide()`; focus stays on the switch), so Previous, Next and Remove cannot act on comments the reader cannot see; switching them on again does not open it. **The command while they are hidden** (`open_for` -> `reveal()`): turns the display on (moving the switch through `editor.on_comments_shown`, which the page sets; the page's handler skips the redraw when the command already did it) and then does what it always does -- opens the comment on those words, or a new one to be written (nothing is made until Save). It removes nothing. It says "Comments were hidden and are shown again." in a toast that stays until closed (Quasar gives a toast `role="alert"`, so it is announced; no separate status region, which would read it twice). ## Undo history (`utils/undo_redo.py`)

`save_state()` snapshots an `EditorState`: the captions **and** the speaker set, copied so a later edit to the live editor cannot reach back into a state already on a stack. Both halves have to travel together — the captions carry which speaker each block belongs to, the list carries which names exist at all, and the list cannot simply be recomputed from the captions on the way back, since a speaker can legitimately exist with no block using it ("Add new", or every block reassigned away). Restoring only the captions left a block naming a speaker the list no longer held: the menu highlighted nothing as current, `prompt_rename` refused to act on that name (it checks membership), and the name introduced by the undone edit lingered as unused forever.

`EditorState.speakers` is `None` for a state saved without one, and `SRTEditor.restore_speakers()` treats that as "this state has nothing to say about the speakers" — it leaves the live list alone rather than emptying it. The set is mutated in place rather than rebound, because the speaker menu and `TranscriptEditor.refresh()` both read it straight off the editor.

`undo()`/`redo()` return the `EditorState`, not a bare caption list, and both call `update_flagged_count()` — the text moving is exactly what changes which words are flagged, and that counter is pushed rather than recomputed on read.

Because the speaker list rides the snapshot, anything that changes it needs a history entry of its own: `add_speaker()` and `remove_speaker()` both call `save_state_for_undo()`, without which they were not undoable *and* the next unrelated undo silently took them back.

Replace (`replace_in_current_match`, `replace_all` in `utils/srt_search.py`) carries the marks along inline (`carry_marks()`) rather than going through `update_caption_text()`, which would take a second snapshot on top of the one already saved — Replace All across many captions has to stay one undo step. Assigning `caption.text` directly, as both once did, skipped retagging altogether: the replaced word came out unmarked, and a replacement of a different length left every mark after it pointing at whatever word had shifted into its position.

**Find is a card in a deck of its own, not a dialog** (`utils/find_panel.py`, `FindPanel`; the state and the matching are `SearchMixin` in `utils/srt_search.py`). It is built like the validation and comments cards (the same `validation-panel` classes, header, live region) with `is-find`, whose stripe is the steel blue `--color-find-line`: the one tone nothing else in the editor has (amber is a warning, red an error, violet review, teal the reader's own edits, pink comments, pale blue-grey what is playing). It is created in `pages/srt.py` **after** the validation card (subtitles) or the comments card (transcriptions), in the same column, so it is the card under it when that is open and the first card when it is not; both formats have it. Find was named "Search" on the toolbar and "Find & Replace" in the dialog; it is now **"Find"** on the toolbar button and in the shortcut list (with "Replace", Ctrl + H) and **"Find and replace"** as the card's title. It is modelled on a word processor's Find, Word being the reference:

- **Every occurrence is a match** (`find_occurrences()`: `search_results` is a list of `(caption index, start, end)`, the term taken as typed via `re.escape`, case ignored unless Aa is pressed; a term of nothing but spaces is no search). It used to be one match per *caption*, which made "3 of 12" wrong whenever a caption held two. One is the current match (`current_search_index`). Enter / Shift+Enter and the header's arrows step through them round the end (`navigate_search_results`).
- **Live.** The field searches as it is typed (`update:model-value`, throttled to the end of the typing, 0.3 s, so the value itself is always current for Enter to read; an Enter that arrives before the look has happened does the look and does not also step). A search begins at the caption the reader is on, so typing does not snap back to the top.
- **Marks.** The words are drawn by the browser's highlight registry (`paintFind()` in `transcript_editor.js`: `CSS.highlights`, `::highlight(find-match)` and `::highlight(find-current)` in `styles.py`) — a heavy dashed underline in the card's colour (a shape, not only a colour), the current match also with a wash. **Only the words are marked, never the caption** (it was both once, with the caption tinted blue after being amber, which read as a validation warning): Validate marks whole captions (amber, red) and has the block, and two cards both tinting it would have fought over it. A caption that is invalid and has a match shows the validation tint, with the match's words underlined in it. The registry rather than wrapped elements because the text is a contenteditable the reader types into: a search must add nothing to it and take the caret nowhere. The server hands over `{id, s, e}` with offsets **as the browser counts them** (`utf16_offset()`: an emoji is two), `set_find()` sends only when they changed, and the component repaints after every re-render (the ranges point at nodes that are gone) and when the marks change, doing nothing when what it would draw is the same as last time (`findSignature`; an update resends every prop). `refresh_display()` looks again before it draws while a term is set, so an edit makes a match or takes one away and the right captions are marked.
- **Replace changes the current match only** and moves to the next one after what was put in (so `cat` → `cat cat` does not find itself), round the end; Replace all changes every one. Both are one undo step. The search is looked at again first, in case the text was typed into since. **Replace is the reader editing the word**: it goes through the same `carry_marks()` as typing does (`update_caption_text`), so a comment, highlight or edit mark on the replaced word behaves exactly as when the word is typed over (one word for one keeps the comment and highlight and earns an edit mark; a longer or shorter replacement keeps them when everything replaced carried them; replacing with nothing drops a comment whose words are all gone). `TestReplaceIsTheSameAsEditingByHand` compares the two paths; keep them on the one function. **A comment taken by a replacement is announced afterwards, not asked about first**: Replace and Replace all count the comments before and after (`comment_count()`) and, when some went, show a warning that says how many and that Undo restores them (`comments_lost_note()`; sticky, with Close, like the other warnings). Asking first was weighed and dropped: deleting a commented word by hand takes its comment silently, so a prompt only on Replace would break the point of the two being one operation, and Undo (one step even for Replace all) already undoes it. Nothing is said when every comment stays.
- **Closing takes the marks off** (`clear_search()`; Esc in either field, the x, and nothing else — the Find button does not toggle, it focuses the field), and focus goes back to the toolbar's Find button. What was in the field stays for the next opening, when it is searched again.
- **Ctrl/Cmd+F** opens it (`SRTEditor.open_find()`), with the words selected in the transcript in the field when there are some (`SELECTED_WORDS_JS`, read *before* the field takes focus, which would move the selection; not for more than a phrase or outside the text). **Ctrl+H** opens it with Replace unfolded; Ctrl only, because Cmd+H hides the application on a Mac and never reaches the page, and the page holds back the browser's own Ctrl+H (history). The field keeps every key to itself (`stopPropagation`) except those two, as the comment box does, so undo and save are not the transcript's while a word is typed.
- `select_caption()` toggles, which is why stepping does not use it for a second match in the caption already on (`reveal_current()` scrolls instead).
- Needs a browser with the highlight registry (Chrome, Edge, Safari 17.2, Firefox 140); without it only the caption's own tint is drawn.

**Every card in the deck can be folded to its header** (`utils/card_fold.py`, `CardFold`; used by `ValidationPanel`, `CommentsPanel` and `FindPanel`). There are three cards that can be open at once, and more to come, so the deck has to be able to give the transcript its room back. A chevron before the heading (a button with a fixed name, `aria-expanded` and `aria-controls` pointing at the body, like Find's Replace toggle; a click on the heading does the same, for the mouse only) folds the card to its header: heading, "3 of 12", Previous/Next and the close button stay and still work; the body goes (`display: none`, so nothing in it can be tabbed to), and so does Validate's filter row. Things to keep when changing a card:

- **The state is `data-folded` on the card's wrapper (`validation-panel-wrap`), not a class on the section**: `ValidationPanel.draw()` replaces the section's classes on every redraw and would wipe it. The CSS keeps the header and every `.sr-only` child of the section, so a live region that must be heard while folded has to be a child of the section *outside* the body.
- **Folding takes nothing away**: a comment being written keeps its text, Find keeps its matches marked, Validate keeps the issue under review. Focus goes to the chevron, since whatever had it is gone.
- **Opening unfolds, following does not.** Validate's `show()`, Find's `open()` (Ctrl+F, Ctrl+H) and a comment opened with the key or the button (`CommentsPanel.show(focus=True)`) unfold the card. Stepping, and the comments card following the caret or a click, leave it as the reader left it. Closing (`close()`, `hide()`) unfolds, so the next opening is whole.
- **While folded, Validate says where the reader is** ("Issue 2 of 5.") in `folded_spoken`, because its body, which is the live region for the issue, is not there. Find's and Comments' live regions were already outside their bodies.
- Folded state is not remembered between sessions or between openings.

## Editor keyboard shortcuts

Two handlers, split by what each needs to know:

- **Block-scoped** (in `transcript_editor.js`, gated on `event.ctrlKey || event.metaKey`): Ctrl/⌘+Enter split (Enter alone does this too), Ctrl/⌘+↑/↓ move a word across the boundary, Ctrl/⌘+Shift+↑/↓ move all the text before / after the caret across it (the word the caret is in goes whole; when that would leave the caption empty it is a merge instead; the event carries the caret `offset`, which a word move does not need; the Shift branches must stay ahead of the plain arrows, which would swallow them), Ctrl+, / Ctrl+. nudge the caption's start earlier / later and Ctrl+Shift+, / Ctrl+Shift+. its end — subtitles only, `SRTEditor.NUDGE_MILLISECONDS` (100) per press, by `event.code` because Shift turns the characters into ; and : on a Swedish keyboard, Ctrl only (⌘+, is the browser's settings on a Mac), no Alt (AltGr); only that edge moves, neither neighbours nor the other edge, an edge stops one step short of the other and at 0 / the media length, overlap is left to the validation, and a run of nudges of the same edge is one undo step (`NUDGE_UNDO_WINDOW`), Ctrl+Shift+Space play the block with `CONTEXT_WORDS` (5) words of speech either side, none further than `CONTEXT_SECONDS` (5 s) from the block (a word beyond that is left out, silence and all, so a long pause is never played) (`playWithContextKey`, Ctrl only like Ctrl+Space itself; the page's own Ctrl+Space handler only takes it without Shift, so the two never both fire; the stop at the end is decided per animation frame in `SRTEditor.PLAY_RANGE_SCRIPT`, next to the player, and gives way if the reader pauses or moves the recording **in either direction** -- told by the player's `seeking` event, which playing never raises, not by comparing positions (that let a jump back keep playing and a jump forward past the end pause) -- after which it simply goes on playing from where the reader put it; nothing here touches focus), Ctrl+M merge with next, Ctrl+D delete, and — subtitles only — Ctrl/⌘+Shift+Enter add after, the keyboard's half of the caption row's own "+", which a transcription has no row for. **One list per format**: `onKeydown` only picks, on `this.subtitleMode`, between `subtitleShortcut()` and `transcriptionShortcut()`, each of which answers `true` when it took the key and `false` to let it fall through to the split branch and the page's own handler. They are deliberately not one shared list — the two agree today, add-after aside, since a paragraph is split, merged, deleted and trimmed exactly as a caption is, but giving one format a key must not silently give it to the other. The server handlers (`TranscriptEditor.merge`/`move_word`/`move_text`/`nudge`/`play_with_context`/`delete`) never cared which format they were in. Each key has to know which block the caret is in — which the page's document-level handler does not. Both lists report through one `report()` helper, which `preventDefault()`s and `flush()`es before emitting, so a pending edit reaches the server before the structure changes under it. **The Shift+Enter branch must stay ahead of the split branch**, which only checks for Enter plus a modifier and would otherwise swallow it.
- **Text moved across a boundary takes its marks with it.** `move_text_before_cursor_to_previous()` and `move_text_after_cursor_to_next()` divide and join, with the same helpers a split and a merge use, everything that is kept as word positions counted from the block's first word: `edited_words` and `highlighted_words` (`split_edits`/`joined_edits`) and `comments` (`split_comments`/`join_comments`; a comment across the caret is on both sides with the same text, as when a block is split). **A new kind of mark kept per word has to be added to both functions** -- left out, it stays at its positions, which are now other words in another block. (The one-word moves, `move_first_word_to_previous`/`move_last_word_to_next`, do their own bookkeeping.)
- **Document-scoped** (in `SRTEditor.handle_key_event`, driven by the page's `ui.keyboard`): save, export, find, undo/redo, play/pause, Ctrl/⌘+G Quick Jump (`SRTEditor.on_quick_jump`, set by `TranscriptEditor`; the page's global JS also `preventDefault`s it, since the browser's own is find-next), and Ctrl+Shift+V validate (subtitles only — a transcription has no line-length or line-count guideline to check).

**Quick Jump** (`utils/quick_jump.py` parses, `TranscriptEditor.open_quick_jump`/`quick_jump` act): a seamless, non-modal prompt with no OK/Cancel — Enter goes, Escape closes, a good jump closes it, a bad one keeps it open with the reason in a `role="alert"` line. Input kinds are told apart by the first character: `#12` a caption number (subtitles only — a transcription shows no numbers, so none is promised), `+30`/`-1:05` relative to the playhead (the caret caption's start, or 0, when there is no player), anything else a time read from the right (`123` is 1:23, `90` is 90 s, `10:` is 10 min, `1::30` is 1 h 0 min 30 s; overflow adds up; decimals allowed in the seconds). A time lands on the nearest caption and in it on the last word that has started by then; out-of-range clamps to the ends rather than erroring, and so does a caption number past the last one (`#900` goes to the last caption, as `+9999` goes to the end); `#0` is still refused, since it is not a number a caption has. The dialog uses `no-refocus` because Quasar would put the focus back on the contenteditable without its caret; closing without a jump calls `focus_caret()` itself. `HINT` is tested against the parser so the text cannot drift from the rules.

`moveword` is the event that finally reaches `move_first_word_to_previous()`/`move_last_word_to_next()` in `utils/srt.py`; both had existed and been tested for a while with **nothing calling them**. `TranscriptEditor.move_word()` refocuses the block being trimmed rather than following the word across, so a second press means the same as the first. Both captions are re-timed from the word data by the editor methods themselves. **A caption with one word cannot give it away, so the move is a merge** with that neighbour (the methods return `"merged"` when they merged, nothing otherwise) and `move_word()` puts the caret at the seam, as any merge does, rather than in a caption that is no longer there.

The Shortcuts dialog is worded for whichever format is open — captions or paragraphs, never "block", which says nothing to either reader — and its contents come from `SRTEditor.keyboard_shortcut_groups()` (title from `keyboard_shortcuts_title()`), separate from `show_keyboard_shortcuts()` that draws them so the wording is testable without a UI, the same way `collect_validation_issues()` is separate from its report. Add-after and validate are the two rows subtitles alone carry. The groups are in the order of the work and the toolbar: Editing, Playback (not "Transport", a sound engineer's word), Navigation (Quick jump, then the Timeline's keys, which work while the strip has focus), History, Tools (Find, and what is specific to the format: Validate for subtitles; highlight, comment and saving a comment for a transcription), File operations (Save, Export). Validate is a tool, not a file operation. Esc is not listed for comments: it is what Esc does everywhere. The nudge rows say how far (0.1 s, `SRTEditor.NUDGE_MILLISECONDS`).

**Modifier choices are deliberate, not oversights.** Ctrl only (never ⌘) for M, D and Shift+V: ⌘+M minimises, ⌘+D bookmarks, and ⌘+Shift+V is paste-without-formatting on a Mac, and taking any of them would take them from the whole window. Note also that macOS binds Ctrl+↑/↓ to Mission Control at the OS level, so the ⌘ variant is the one that actually reaches the page there — which is why the word moves accept both.

## Following the video (`TranscriptEditor.follow_video`, `pages/srt.py`)

`video.on("timeupdate", transcript.follow_video)` (`pages/srt.py`) drives two separate things from one server round trip, a linear scan of `editor.captions` for the one whose `[get_start_seconds(), get_end_seconds())` window contains the player's current time (`ui.run_javascript` reads `document.querySelector("video").currentTime` — timeupdate itself carries no position):

- The editor's own active-block highlight (`TranscriptBody.set_active` → `activeId` → `.transcript-cell-active`, and the scroll that follows it) — gated on `editor.autoscroll`, the "Follow audio"/"Autoscroll" switch.
- The subtitle overlay drawn over the video itself (`TranscriptEditor.set_overlay`/`draw_overlay`, subtitles only — `pages/srt.py` only creates and wires the label when `data_format == "srt"`, since a transcription's own blocks are a speaker's whole turn, not a short timed cue, and would cover half the frame) — **not** gated on `autoscroll`: it is a preview of what a viewer sees, wanted whether or not the reader also has the editor scrolling to follow along. Hidden (`set_visibility(False)`) between two captions or past the last one, the same as a real subtitle track would be. Gated on its own switch ("Subtitle overlay", `editor.show_subtitle_overlay`, persisted under `OVERLAY_SHOW_KEY`) — **on** by default, unlike the review markings, since it shows what a viewer would see rather than adding anything to read; `set_overlay_enabled()` redraws at once rather than waiting for the next timeupdate, which never comes while the video is paused, and that is exactly when the switch tends to be used. `draw_overlay()` splits the caption on its own `"\n"` and gives each line its own `ui.label` (`.video-subtitle-line`), so the overlay breaks exactly where the editor does rather than wherever the width happens to run out — the same split `caption_line_counts()` uses for the character guideline, and a blank line still gets an element of its own so the lines under it do not move up. Labels, never `ui.html`: a caption's text is user content, not markup to trust. `refresh_overlay()` redraws it after an edit as well as on timeupdate — the reader is very often paused while editing, and timeupdate does not fire then, so the overlay would otherwise keep showing the caption as it read before. Hooked into both `changed()` (typing, which `set_text` deliberately reports without a re-render) and `refresh()` (split, merge, delete, retime, undo — any of which can change *which* caption covers the moment being played, not just what it says). It re-derives the caption from `overlay_seconds`, the time the player last reported, rather than holding a reference to the caption itself: undo and the structural edits swap the `SRTCaption` objects out wholesale, and a kept reference would point at one no longer in the list. Nothing redraws before the first timeupdate has given it a time to work from. `_set_overlay_text()` only redraws when the caption actually changes, since timeupdate fires several times a second and mostly lands on the same one — the remembered value starts as the `UNDRAWN` sentinel rather than `None`, which is itself a real value here ("nothing is playing") and would otherwise swallow the first tick that lands in a gap. Each line is drawn `white-space: nowrap` and the overlay's own `font-size` is `min(1rem, calc(85cqi / (var(--subtitle-char-limit) * 0.55)))` — a wrap inside a line the editor did not break shows a viewer a break the subtitle file does not have, so instead of letting the box wrap, the type shrinks with the frame until a line of the guideline's full length fits on one. `--subtitle-char-limit` is set on the overlay element in `pages/srt.py` from `settings.CHARACTER_LIMIT` rather than hard-coded in the stylesheet, and `.video-frame` carries `container-type: inline-size` for `cqi` to resolve against the video's own width (the splitter can leave it narrow). `.video-frame` gives the video's wrapping `div` a `position: relative` neither `ui.video` nor the card around it otherwise has, for the overlay's `position: absolute` to anchor against; `pointer-events: none` on the overlay keeps it from swallowing clicks meant for the native controls or a click-to-pause anywhere else on the frame. `bottom` is a fixed `3rem`, not a percentage of the frame's own height -- a percentage once put the overlay on top of the native control bar (a fixed height itself) on a short or wide video, hiding the seek bar underneath its own opaque background rather than sitting above it.

**A click on a caption always goes to that caption.** `time_at_offset()` answers `None` for a word that cannot be placed in the recording (one the reader wrote, or one the model transcribed without a timing), and `seek()` used to do nothing at all with that — no seek, no overlay, no active block, which reads as the editor having missed the click. The refusal is right only while the recording is **inside that caption already**: that is the case the rule was written for, a reader listening to a caption and clicking a word in it, where jumping back to its first word is worse than staying put. Coming from anywhere else the click is asking for the caption itself, there is no position within it to refine, and `seek()` falls back to its start. "Anywhere else" is decided from `overlay_seconds`, the last position the player reported; before it has reported at all, nothing says the recording has left the caption, so the rule stands as written.

**A seek the editor asked for itself does not wait to be told about it.** `follow_video` now only reads the player's time and hands it to `TranscriptEditor.moved_to()`, which is what marks the active block and draws the overlay — and everything that moves the recording deliberately (`seek()` from a click in the text, `select_from_timeline()`, `create_caption()`) calls `moved_to()` with the time it just asked for. Setting `currentTime` to the value the player already holds moves nothing and so fires **no timeupdate at all**, and the first caption of a recording usually starts at 0, exactly where a freshly opened player sits: clicking it seeked nowhere, nothing reported back, and it alone drew no overlay and lit no block.

There is no bisect index over caption time windows the way `caption_words()` has one over word midpoints (`utils/srt_review.py`) — `follow_video` re-scans the full caption list on every tick, which is fine at typical caption-list sizes and timeupdate frequency.

## Caption timeline (`utils/speech_timeline.*`)

Follows [SUNET/scribe-ui#126](https://github.com/SUNET/scribe-ui/issues/126) — read it before changing the component's shape; the decisions below are its decisions, not incidental.

A strip under the video showing where someone is talking, where the silences are, and where the captions divide the recording. **Not a waveform**: the runs come from `ReviewMixin.speech_runs()` over the word timings the transcription already carries, so nothing is decoded and the recording is not fetched a second time — decoding an hour of audio in the browser costs over a gigabyte of PCM, and `utils/video.py` answers every request with the whole file (it returns `206` without actually slicing a range), so a second fetch is a second full download. What it cannot show is loudness, music or noise; a real waveform needs peaks precomputed server-side (ffmpeg) and served as their own endpoint.

- `speech_runs(gap=0.3)` merges words closer together than `gap` into one run — the space between two words in a sentence is not a silence anyone means, and one bar per word draws a picket fence. Words with no timing are skipped rather than placed anywhere.
- `speech_duration()` is the later of the last word's end and the last caption's end: a caption can be stretched past the last thing said and still has to fit on the strip. The component takes the later of that and the video's own `duration` once the player knows it, since a recording usually runs on past the last word.
- **The playhead is not a prop.** The component finds the `<video>` itself and follows it — `timeupdate` several times a second, plus `requestAnimationFrame` while playing (timeupdate alone is visibly steppy across a strip this wide) — and clicking seeks by setting `currentTime` directly. A round trip per tick to move a line two pixels is not worth taking.
- **The playhead is fixed in the centre** and the recording scrolls behind it. Deliberately *not* clamped at either end: clamping slides the playhead off centre exactly where the reader works most, on the first and last captions. What lies before 0 or past the end is shaded (`--timeline-void`) rather than left as blank strip.
- **Three states, never conflated**: the caption being *edited* (`currentId`, sent from the server — that is where it is known), the caption being *played* (`playingId`, computed locally from the playhead, since pushing it would be a round trip several times a second), and the caption under the *pointer* (`hovered`, local). Hovering one on the strip must not take the text editor's focus off another, which is why `onLeave` clears only the hover.
- **A caption is a bracket pair**, `[` and `]`, not a block: when one caption ends exactly where the next begins — the common case — a block cannot say which of the two touching edges belongs to which caption. The whole interval is the hover target, so nobody has to aim at a thin line; the brackets thicken when hovered, which is also when they can be grabbed. Each carries its own `#number`, drawn only when it fits, so the same caption can be found in the text editor.
- **Speech is secondary to caption timing** (the issue is explicit): drawn quietly along the top in `--color-text-muted`, with the captions below it in the brand colour.
- **A caption made this way has no timed words in it**, whatever it covers: its text was typed by hand, so it aligns with none of the words under it (`aligned_words()` returns all `None`), and a caption dragged out of a silence has none under it to begin with. `time_at_offset()` — which `seek()`, a click in the text, goes through — falls back to the caption's own start when *nothing* in it is timed, exactly as it does for a job with no word data at all. Its "an edited word has no honest time to move to, so stay put" rule is about telling one edit apart from the timed words around it and needs there to be timed ones; without the fallback, clicking such a caption in the text moved the recording nowhere, so the subtitle overlay went on showing whatever the player was still parked in — or nothing, when that was a stretch no caption covers. Note the check is over the *aligned* words, not `caption_words()`: a caption dragged over speech that had no caption — the whole point of the feature — does cover words, and testing for those found the silent case only.
- **Clicking a caption asks for that caption** — `selectcaption` → `select_from_timeline()` seeks **to its start**, focuses the block in the text editor and marks it current. Clicking the strip itself asks for that moment, to the pixel, and changes nothing else — that click never reaches `select_from_timeline()`. It once seeked to the middle of the caption, on the reasoning that the frame where a cue begins shows what is about to be said rather than what the cue covers; that was reported as a bug, since a reader clicking a caption is asking to play it and landing halfway through means the first half is never heard without seeking back by hand. A caption *just dragged out* still gets its middle (see below) — there the start is the edge the reader has this second placed themselves. `mark_current()` is also called from `seek()` (a click in the text) and `scroll_to()` (search, autoscroll), so all three ways of moving to a caption agree.
- **It can be dragged to the foot of the page.** A grip (`⠿`) in the legend row moves it — not the strip itself, which already means taking hold of a caption, and one gesture cannot mean two things. Letting go below `DOCK_AT` (70% down the window) docks it; above, it goes back under the video, and the legend says which while the grip is held. Docked it is `position: fixed` from where the menu rail ends to the right edge — the rail is fixed too, so `left: 0` runs underneath it, and it is not a fixed width either: `followTheRail()` measures `.q-drawer--left` and the component watches it with a `ResizeObserver`, a `transitionend` (Quasar animates the rail) and a window `resize` — rendered through `<Teleport to="body" :disabled="!docked">` while docked — `position: fixed` alone was not enough, because the strip lives inside the splitter and the splitter's separator is a positioned element that drew a line straight down through it. Teleport moves only where it renders: same component instance, same listeners, same state — and it holds `DOCKED_WINDOW = 60` seconds instead of 20: three times as wide, so roughly the same seconds per pixel, which is what actually decides whether a caption edge can be seen and aimed at. A fixed strip takes no space of its own, so `markDocked()` puts a `timeline-docked` class on `document.body` and the stylesheet pads `.nicegui-content` out of its way. The position is persisted under `TIMELINE_DOCK_KEY`, but the prop is called `startDocked` and is only read at mount: the component owns the position from then on, and a prop pushed back mid-session would yank the strip out from under the reader.
- **It shows twenty seconds at a time undocked** (`WINDOW = 20`, within the 10–30s the issue asks for), because an hour across the pane is roughly a minute per pixel and no caption edge can be seen at that scale, let alone aimed at. Fixed, not offered as a choice — a strip whose scale changes underfoot is harder to read, not easier — and a recording shorter than the window simply shows all of itself. The view follows the playhead, centred on it and clamped at both ends (a window scrolled past the start would show empty space where the recording is not). A label says which part is on screen (`12:30–13:30 of 42:15`), since one stretch of speech looks much like another.
- **Zoom is a factor of the window, in doublings** ([#134](https://github.com/SUNET/scribe-ui/issues/134)): `zoom` between `ZOOM_MIN` (0.25) and `ZOOM_MAX` (4), and `visible()` is `(WINDOW or DOCKED_WINDOW) / zoom`, so "Reset zoom" is always the window the strip started with, docked or not. It changes only how the strip is drawn — never a caption, the playhead or the player — and is not remembered (it is a way of looking at one recording, not a preference like the dock). Zooming out is refused once the whole recording is on the strip. Snap and grip distances are in pixels, so they follow the zoom without any change.
- **The strip is a slider** (`role="slider"`, focusable, `aria-valuetext` in words: "0:12.3 of 5:00, in caption 14"). Arrow keys move the playhead by a fortieth of what is on the strip, Page Up/Down by a whole strip, Home/End to the ends, Shift+↑/↓ or `+` `-` zoom, `0` resets — all through `seekTo()`, which sideways wheel scrolling ([#128](https://github.com/SUNET/scribe-ui/issues/128)) uses too: the strip moves at once, the player is told once a frame, and `follow()` ignores the player while a move is waiting. Ctrl/Cmd with a *key* (plus, minus, 0) is the browser's zoom and is left alone, as is Cmd with the wheel. **Ctrl with the wheel over the strip is a pinch and zooms the strip**: a trackpad pinch arrives as a wheel with `ctrlKey` set (Chrome, Edge, Firefox, on a Mac too), so `onWheel()` cancels it and `pinch()` multiplies the zoom by `exp(-deltaY * PINCH_SPEED)` (spread fingers = negative `deltaY` = in), capped per event by `PINCH_MAX` so a mouse-wheel notch is a firm step; Safari sends `gesturestart/change/end` instead, taken by `onGesture()`. Both go through `zoomBy()`, which keeps the buttons' limits, does nothing while a caption is dragged (the page's own zoom is still cancelled), and says the new width in the status region only once the zoom has stood still for `PINCH_SETTLE` (a screen reader told at every step says nothing else). Outside the strip Ctrl+wheel is still the browser's zoom. Only *sideways* wheel movement is taken, up and down is the page's — except for the tail of a swipe (200 ms after the last sideways event, `SWIPE_LATCH`), which stays the strip's so it does not scroll the page mid-gesture. A swipe that reaches the end must not become the browser's "Back": `overscroll-behavior` does nothing on the strip (not a scroll container), so `holdSwipe()` sets it to `none` on `<html>` and `<body>` while the pointer is over the strip and `releaseSwipe()` puts it back on leave, hide and unmount. `aria-valuenow` is **not** updated every frame: only on a move the reader made, when the recording stops or lands, and on focus — a screen reader told about every frame says nothing else.
- **The ruler** is drawn in the canvas, in a `RULER` (16 px) band along the top edge; the strip is that much taller than before (`calc(4.5rem + 16px)`, and the docked page's bottom padding likewise) and everything else on it keeps its proportions in what is left. `rulerTicks()` picks the coarsest row of `RULER_STEPS` that leaves `LABEL_GAP` px between two labels, so the unit changes with the zoom by itself (tenths of a second up to hours); small ticks are left out when closer than `MINOR_GAP` px; nothing is marked outside the recording. Ticks are counted as whole multiples of the step, not added up, so tenths do not drift. The ruler is a picture: the strip's value for assistive technology is the slider's `aria-valuetext`, and the colour is `--timeline-ruler`.
- **Moving the strip with the grip shows where it will land** ([#127](https://github.com/SUNET/scribe-ui/issues/127)): `ghost` is `"foot"` (a fixed placeholder along the bottom of the window, teleported to `body` like the docked strip, `calc(10rem + 22px)` tall — what the docked strip measures, 182 px at the default text size), `"rest"` (an in-flow placeholder where the strip sits under the video, as tall as it measured there: `noteRestHeight()` runs in `setDocked` as the strip leaves, because docked the strip is somewhere else) or null (not moving, or over the place it already is). Both say "Release to dock Timeline here" and are the only thing that says what letting go will do (the strip's legend used to carry the same in a line of its own). Both are `aria-hidden` and `pointer-events: none` so the drop goes through. The component's root is a fragment — the strip's Teleport, then the placeholders — **not** a wrapping element: docked, an empty element would still take a gap in the column it sits in.
- **The controls beside the strip** (dock, zoom out/in/reset, add caption at the playhead) are a `role="toolbar"` tray in the first legend row. The key stays at the left. The playhead is always in the middle of the strip, so where the strip is wide the tray sits under it: the legend is a grid of `1fr auto 1fr` (the key in the first column, which cannot wrap and so is never narrower than it; the tray, with equal margins, in the middle; the hint across all three on a row of its own below) inside `@container (min-width: 30rem)` on `.speech-timeline-wrap` (`container-type: inline-size`, so the legend asks how wide the *strip* is, not the window). Where there is not room the first column is the key's width and the tray follows it at the same distance as before, so it moves between the two places continuously, never jumps and is never over the key (about 774px of strip with the default text size; the key's width scales with the text). Narrower than 30rem the legend is the wrapping flex row it was (`.speech-timeline-keyrow` is then `display: contents`); the hint has a row of its own, so the tray's width never moves it; there is no range text — "where am I" is the ruler — and it is in the caption actions' own style, one tab stop with arrow keys between the buttons. Icons only, so every one is named; the dock is `aria-pressed` with a fixed name rather than a label that changes; a button at the end of its range is `aria-disabled`, not `disabled`, so focus is not dropped. Docking teleports the strip and a moved node loses focus, so `toggleDock()` puts focus back on the button. The tray is revealed by pointing at the strip, by the keyboard being on the strip or a button (`body.scribe-user-is-tabbing`), and always where nothing can point (`hover: none`) — opacity only, so it stays in the tab order and its space is reserved.
- **Dragging where no caption is makes one.** The strip is where a reader can see that nothing covers a passage of speech, so it is where they can say that something now does — rather than adding a caption after some other one and dragging it across. `startCreate()`/`onCreateMove()`/`finishCreate()` mirror the retime drag: both ends go through the same `snap()` (so a new cue meets its neighbour flush, or lands on the ends of a phrase), and both are kept inside `gapAt()` — the stretch around the point pressed that the captions leave free — since two cues over the same instant is one of the errors "Validate" reports and a gesture should not be able to make one by accident. `create_caption()` re-checks the overlap on the server (captions can have moved since the strip was last drawn) and otherwise appends, `sort_captions()`s (a caption's number *is* its position, and this one was appended rather than inserted), and then does everything a click on the strip does — **seeks the recording to the middle of the new caption** (not its start: that is the edge the reader has this second placed themselves, so there is nothing to show them there — unlike a *click* on an existing caption, which does go to its start), hands it the caret the way "Add caption after" does (it starts empty, and its text is the next thing wanted), and marks it current. The seek is what keeps the frame under the subtitle overlay honest: the overlay draws whatever caption covers the play position, and a caption dragged out of the empty stretch around the playhead — fixed at the centre of the strip, so that is usually where the empty stretch is — covers it, so the text appeared over a frame from somewhere else entirely as it was typed. A gesture that barely travelled is still a click, and means that moment: `finishCreate()` refuses anything under `MIN_NEW_SECONDS` and leaves `onClick` to seek. While in flight it is drawn like any other caption under `NEW_CAPTION` (`0`, which `renumber_captions()` can never produce) and without a number, since it does not have one yet. **The "Add caption at playhead" button in the strip's legend row is the same gesture without a pointer** (`addAtPlayhead()` → `createatplayhead` → `TranscriptEditor.create_at_playhead()`): it names a moment rather than a stretch, so the server works out the stretch — `NEW_CAPTION_SECONDS` from the playhead, up to the next caption when that comes sooner, and no further than the recording's own length (the player's `duration`, not the `duration` prop, which is how far the *speech* goes) — and then calls `create_caption()`, so it is empty, takes the caret, seeks to the middle of it and is one undo step. The playhead is read from the player (`video.currentTime`), not from `position`, which lags it by a frame or two. A playhead already inside a caption (`start <= at < end`) makes nothing — two captions over one instant is a Validate error — and moves the caret into that caption and says so; less than `MIN_NEW_SECONDS` of room says so too. It is a `q-btn` with the same `editor-btn editor-toolbar-btn editor-outlined` classes as the validation card's buttons, a size down (`.speech-timeline-add`), so the strip's panel and the validation panel read as one kind of thing. It goes with the strip: switched off with the Timeline switch, it is not there.
- **A caption can be dragged**: an edge moves that edge, the middle moves the whole cue, and an edge is taken before the body when the pointer is within `EDGE_GRIP` of one. `captionAt()` picks the **nearest** edge of any caption, not the first caption in the list that happens to be in range: two cues close together both answer to a point between them, and taking whichever came first meant reaching for one caption's end and getting the next one's start — and a caption shorter than the grip could only ever be taken by its start, since that check came first while both edges were in range. A tie is broken by **which side of the edge the pointer is on**: where one cue ends at exactly the instant the next begins the two edges are the same instant, so approaching from the left takes the first cue's end and from the right the second cue's start. Any fixed preference makes one of the two unreachable — a caption butted against its neighbour could not have its start dragged at all. The hover readout names the edge (`caption #12 end`) so this is visible before the drag starts. A dragged edge snaps to **the edges of the other captions first** (`CAPTION_SNAP`, a wider reach than anything else): two cues meeting exactly is something a reader means, while a cue landing a hundredth of a second from its neighbour — a gap no viewer can perceive, but a gap in the file — never is. Only when no caption is in reach does it fall back to the edges of a run of speech (`SNAP`), which is where a cut belongs when it is not against another cue; failing both, it lands where the pointer is. The dragged caption is excluded from its own candidates, or it would snap to the edge it is being pulled away from. The drag continues off the strip (listeners on `window`) and the caption is drawn where it *would* land while it is in flight. On drop it emits one `retimespan` carrying both ends, which `TranscriptEditor.retime_span()` applies through `apply_time()` — which calls `SRTEditor.sort_captions()`, since a caption's number *is* its position in the list and a retime can move it past a neighbour: without it the text editor went on showing the caption where it used to be, numbered to match neither its own timing nor its bracket on the strip (the sort is stable, so two captions starting at the same instant keep the order they had). One event, so **one undo step**: two retimes would mean pressing undo twice to put back one gesture. A refused drag (an end before its start) calls `refresh()`, since the strip is already drawing the caption where it was dropped and nothing else would put it back. A click event follows the mouseup that ended a drag, so `onClick` ignores one after any real movement — seeking to wherever a drag finished is never what was meant.
- **The "Timeline" switch is a prop (`shown`), not `set_visibility()`.** NiceGUI hides an element by putting a `hidden` class on it, and this component's template is rooted in a `<Teleport>` — not a DOM node, so a fallthrough class has nothing to land on and the switch did nothing at all. `SpeechTimeline.set_shown()` sets the prop; the wrap is `v-show` (not `v-if`, so the canvas and the listeners `mounted()` set up survive), `markDocked()` ands it into the body class so a hidden docked strip stops reserving its padding, and the watcher calls `settle()` on the way back, since a strip that was `display: none` has no size to have measured itself against.
- Only the runs, the captions and the duration are sent. `TranscriptEditor.refresh_timeline()` redraws the captions from `refresh()`, alongside the overlay, since a split, merge, retime or undo moves them; the runs never change.
- **`draw()` runs on every animation frame while the recording plays**, so what it does per frame matters: the canvas is resized only when its size actually changed (assigning `canvas.width` reallocates the backing store) — which is why `shrinkCanvas()` clears the remembered size along with the pixels: hiding the strip and showing it again hands back exactly the box it had, the size string matched, and `draw()` painted into the 0×0 store `shrinkCanvas()` had just left, the custom properties are read once into `palette` and dropped only when they could have changed (a `MutationObserver` on `document.body`'s class for the theme, and docking, which moves the strip somewhere with a different background), and only the runs and captions overlapping the visible window are drawn — `within()` bisects into each time-ordered list and steps back over a long entry that begins before the window and reaches into it. `visibleCaptions()` adds the dragged caption back in, since it is drawn where it *would* land, which can be outside the window its own timings still put it in.
- A canvas cannot read a stylesheet, so the colours are custom properties on `.speech-timeline` that the component asks for by name — which is what lets dark mode change them without the component knowing. It redraws on `ResizeObserver` (the splitter changes its width) and at `devicePixelRatio` (or the playhead lands between pixels).
- **It names what it draws.** Bars, gaps, ticks and a playhead mean nothing on their own, and a canvas has no elements to hang a tooltip on — so a small key sits under the strip (each swatch drawn as the shape it stands for, not a uniform square), and pointing anywhere on the strip shows a readout of the time, whether anyone is speaking there, and which caption covers it, worked out from the same runs and boundaries it draws. The readout is `pointer-events: none`: it sits over the strip the reader is trying to click.
- Offered only for subtitles, and only when `editor.words` is non-empty — there is nothing to draw without timings, and nothing to time in a transcription, whose blocks are a speaker's whole turn rather than a short cue (the same gate the subtitle overlay has). The same component-registration gotcha as `transcript_editor.js` applies: keyed by file content at import, so a `.js` edit needs the process restarted.

## On a phone

What a phone is for here is **recording something and starting a transcription of it**. Editing is not: the editor puts a video, a caption list and a timeline side by side, which is a desk. `/srt` says so for itself on a small screen (`.editor-too-small`, `pages/srt.py`) rather than being shrunk into something that technically fits — a sentence and a way back, not a redirect, because a reader who followed a link there should be told what to do rather than bounced to where they came from. Which of the two is drawn is left to the stylesheet: the server cannot know how wide a phone is, and a reader turning a tablet in their hands should not have to reload.

**One breakpoint, 700px** — the difference between a window and a hand, not a scale of sizes. Below it:

- **The menu rail gives its width back.** 56px of a 390px screen went to icons nobody was looking at. Collapsed it is 0 wide; opened it is drawn *over* the page rather than beside it, since there is no room to put anything beside anything. Quasar writes the page container's padding inline from the drawer's own width, which is why the rule has to say `!important`. A menu entry clicked there closes the menu before it navigates (`navigate_closing_menu()` in `page_init`): the entries are real links and `drawer_open` is remembered per user, so the next page came up with the menu drawn over it again. The click is intercepted in the browser only below 700px and only for a plain click — a new-tab click is left to the link — and the server marks the menu closed *then* navigates, so the new page is not asked for before it is. Only marked, not collapsed on the page being left: collapsing it there flashed Quasar's mini icon rail before the next page arrived.
- **A finished job is *viewed*, not edited.** The card's action for a completed job says **View** and opens `/view` (`pages/view.py`), a read-only page: the recording at the top (sticky, since the point of tapping a passage is hearing it — sticking *below* the header, whose height is measured in the page into `--view-header`: the header is `position: fixed`, so a sticky element stopping at 0 parks underneath it and loses its top edge, and the height is not a constant because the header carries the announcement banners and gets shorter when one is dismissed), the transcription under it, the passage being played marked, and a "Follow audio" switch that scrolls the list with it. It is the same fetch and the same parsing the editor does — an `SRTEditor` is built only to run `parse_srt`/`parse_txt` over the result, so what a caption is (its timing, its speaker, where the paragraphs fall) is decided in one place for both pages — and nothing on it writes: no save, no export, no `TranscriptEditor`, no editor state on the server behind it. Marking and seeking are done **in the page** rather than driven from the server the way the editor's own `follow_video` is: a round trip several times a second to move a highlight is not worth taking when nothing on this page holds state. A caption's text is drawn with `ui.label`, never `ui.html` — it is somebody's speech. Which page a row opens is the *caller's* decision (`table_view` vs `table_click`, both onto `open_result()` in `utils/common.py`), not something worked out again from the width of the screen: the card emits `table_handle_row_view`, the desktop row still emits `table_handle_row_click` and still says Edit. `/srt`'s own too-small notice offers the same page ("View transcription") rather than only turning a phone away.
- **A row of the jobs table becomes a card.** Seven columns are unreadable on a phone and the row's own action — Transcribe, or Edit — is the whole of what anyone came to the list for. Quasar's `grid` prop does the drawing and the table's `item` slot fills the card in: filename, type and status, the dates, a checkbox so Delete still works, and the action as a full-width button. Both controls in the card carry an `aria-label` naming the row's own file, the same way the desktop table's checkbox and action button do (WCAG 4.1.2) — grid mode is a second rendering of the same rows, so it needs the same names. **The width it switches at and the width the stylesheet dresses the cards at are the same number**, and `tests/test_mobile_layout.py` is the only thing that says so — cards styled for a hand appearing at a different width than the cards themselves is a stretch of widths nobody laid out.
- **`window.innerWidth < 700`, not `$q.screen.lt.md`.** NiceGUI evaluates a `:`-prefixed prop with `eval()` in the *page's* scope, where Quasar's `$q` — a component property — does not exist; a prop that throws is dropped without a word, which is what happened. Read once, when the table renders, which is what a phone needs; a desktop window dragged across 700px keeps its columns until the page is opened again.
- **Nothing may be wider than the screen.** Several cards name a minimum width — 400px for the upload dialog, 500px for the shortcuts dialog and the user settings card — and a minimum wider than the phone takes the whole page sideways with it. The upload dialog asks for `min(400px, 100%)`; the rest are answered by the stylesheet (`min-width: 0 !important` on cards in a dialog and cards in the page), since there are too many to keep finding by hand.
- The table's toolbar stacks and its four actions — Delete, Export, Transcribe, Upload — become a two by two grid of identical cells (`.jobs-actions`, `display: grid`), since they are peers and none of them is the action of the page; wrapping them sized each by its own label, which put three on one row and one alone on the next. Four across a 390px screen leaves no room to read "Transcribe", which is why it is a grid and not `flex: 1 1 0`. The header stays one row (`.q-header` `flex-wrap: nowrap`; `.header-brand` shrinks, `.header-actions` does not) — left to wrap, the theme and help buttons dropped onto a line of their own under the logo — and the product name in it truncates.
- **`playsinline` on every `<video>`** (`/srt` and `/view`): iOS plays a video fullscreen without it, which on `/view` means the transcription disappears the moment a passage is tapped — since tapping one is what plays it. `webkit-playsinline` is the same thing for older iOS.

Ported from transcribe-ui, where the layout was checked in a browser at phone width. The recorder has its own phone rules (`.recorder-*` under the same 700px breakpoint) — see "Recording".

## Recording (`pages/record.py`, `static/recorder_engine.js`)

Recording from the browser's microphone, on a computer or a phone/tablet, sent to scribe-backend while it is recorded and made into a job the moment it stops. Built around one rule: **audio is kept in the browser only while it cannot be sent to Scribe.** The use case that decides everything is a lecturer leaving a phone on a lectern for ninety minutes; any crash, reload, flat battery, lost wifi, backend outage or expired sign-in must cost at most the last second. The backend's half is `routers/recording.py`/`utils/recordings.py` in scribe-backend (branch `recording`); read its AGENTS.md section alongside this one.

- **Its own page, `/record`, not a dialog on `/home`.** `reconnect_timeout` is six hours (`RECONNECT_TIMEOUT`): past the timeout NiceGUI reloads the page and a reload stops the `MediaRecorder`. The recording would survive (see below), but a lecture should not be cut into parts by a dropped wifi. "Upload" on `/home` opens the upload dialog directly; recording is reached from the drawer's *Recorder* entry.
- **NiceGUI's own reloads are held off while recording** (`guardReloads()` in `utils/recorder.js`). `nicegui.js` reloads the page by itself when a reconnect attempt times out (`connect_error: timeout`, NiceGUI #198) — which is what a computer waking from sleep or moving between networks runs into, whatever `reconnect_timeout` says — as well as on a refused handshake, on a server-requested `try_reconnect`, and when the server cannot replay the messages a reconnect missed (`outbox.py` `try_rewind` sends a bare `window.location.reload()` through `run_javascript`; that one message is emptied, every other `run_javascript` passes). While a session runs those four socket handlers are replaced: socket.io keeps reconnecting on its own, the handshake is made without the reload behind it, and a page that really is stale (handshake refused, or the server's own reload) only says so after Stop, with a Reload button — a reconnect that merely timed out is not stale, since the retry that follows either restores the page or is refused, and warning on the timeout alone showed the banner after every Wi-Fi drop that recovered fine — since recording and uploading need no socket. Stale also hides NiceGUI's own "Connection lost" popup, and the page shows its own banner even while recording — for as long as the socket is actually down (`connected`, from the socket's own `connect`/`disconnect`), since `stale` is one-way and a connection that comes back should not go on being reported lost: a server restart drops the client, the reconnect is refused (`Implicit handshake failed`), socket.io never retries a refused connection, and the popup otherwise stayed up for good over a recording that was going on fine. Outside a recording the original handlers run untouched. **The server's reload fired after every reconnect**, not only when something was really missed: `nicegui.js` puts `next_message_id` in the socket's query once, at page load, and never moves it on, so each reconnect asked `try_rewind` for a message long since pruned by the acks. A `reconnect_attempt` listener (always on, not only while recording) copies `window.nextMessageId` into `socket.io.opts.query` first, so the server replays just what was missed and a reload means the messages really are gone. `tests/test_recording.py` pins the `nicegui.js` code this reaches into, so a NiceGUI upgrade that moves it fails a test rather than silently unguarding the recorder. `beforeunload` is still the last line: it is what asked "Leave page?" before this existed.
- An upload that is not going through says why, with the server's status in it (`Scribe is not answering right now (404).`) — a silent status is how the `/api` routing mistake below went unnoticed.
- **Audio is held in memory, and written to IndexedDB only when sending fails.** Chunks arrive every second (`CHUNK_MS`, `MediaRecorder.start(timeslice)`) into `buffers` (engine-level, by recording id, plaintext, this tab only), strictly in order, one writer at a time (`Session.flush()` is single-flight — two writers wrote the same chunk under two numbers). The first failed send of a *live* recording calls `spill()` from `fail()`: what is in memory is written to IndexedDB and `meta.spilled` makes `writeAll()` write every chunk after it too (chunk and count in one transaction; a failed write keeps the chunk in memory and retries). A sync round that catches up clears `spilled`, so new audio goes back to memory; chunks already written stay until their part is sent. There is no check between the flag and the `buffers.set()` in `writeAll()`, which is what keeps `spill()` from missing a chunk. `finalize()` sends whatever is still only in memory while the recording is still marked live (no other tab touches it then), or spills it if it cannot or the backlog is over two parts, since nothing holds a tab's memory once its session ends. **The recording's record is written from the start regardless** — without it a crash would lose track of the parts already on Scribe and the backend would sweep them — but it holds no audio, and its name is encrypted (`nameSealed`, via the wrapper around the raw store; `name` is `null` while there is no key, and a null is never written back over the sealed one). ArrayBuffers, not Blobs (Safari). No IndexedDB at all falls back to memory and the page says a crash will lose it. **Nothing is kept on the device past 7 days** (`KEEP_MS`): `refresh()` deletes a recording whose `updatedAt` (the last chunk recorded) is older than that, here and on the backend, unless another tab holds it -- the same 7 days the backend keeps an unfinished recording (`RECORDING_ABANDON_HOURS`) and a job keeps its files, so no kind of recording outlives the rest. Everything written is AES-GCM encrypted (WebCrypto) first, bound to its recording id and position by the additional data so a chunk moved elsewhere does not read. The key comes from `GET /record/api/key` (`recording_store_key()` in `utils/helpers.py`: HKDF over the browser key and `STORAGE_SECRET`, salted with the browser id, per owner — the same material `storage_encrypt` uses), is imported non-extractable and held in memory only; a reload asks again. No key, no recording (`NoKey`): the page was served a moment ago, so the server is there. Metas left by the older unencrypted version (`encrypted` unset) still read raw.
- **Recovery**: a meta still marked `recording` whose tab is gone becomes `stopped` + `interrupted`, whole up to its last chunk. "Gone" is decided with a Web Lock held for the life of the session (`scribe-live-<id>`, taken *before* the meta is first written and let go after its last write), timing only as a fallback where there are no locks. With locks the answer is immediate — the list's `elsewhere` ("Being recorded in another tab", which also disables Start) comes from the lock, not from how recently the meta was written: after a reload mid-recording the meta looks fresh for a while, and judging by that told the reader their own, now-dead recording was running in another tab — declaring a live recording over would offer it for upload, cut short, while it is still being recorded. The microphone taken away (a call, another app) ends the session the same way, and the page offers **Continue recording** as a new part. What a recovered recording holds is worked out by `available()`: parts the record says are on Scribe, then chunks in IndexedDB, up to the first gap — whatever was only in the dead tab's memory went with it (online, the part not yet sent: at most `PART_CHUNKS`, five seconds). One with nothing left is deleted here and on the backend. `syncOnce()` never touches a recording that is live in another tab: its audio is in that tab's memory.
- **Parts go to the backend while recording, and leave the browser once confirmed.** Every complete part (`PART_CHUNKS`, five seconds) is `PUT` through `/record/api/<id>/part/<n>` to the backend's `/api/v1/recordings/…`, which encrypts it as it arrives; on a 200 the engine drops that part from memory and from IndexedDB (`dropChunks`, one transaction with the meta's `sent` list). Online, nothing but the record is written; offline, parts wait in IndexedDB and drain when the connection is back. **Stop is finish**: the rest is sent and `POST …/finish` makes the job at once — no Upload step — and `markUploaded()` deletes the recording from IndexedDB entirely (`finishedHere` keeps it on screen for the rest of the page's life, so the list can say where it went). A recording cut short (microphone taken, tab crashed) is *not* finished by itself: it waits with Upload and **Continue recording**. The engine asks `GET …/<id>` what the backend holds before sending; a part in `sent` that the backend no longer has (its 7-day sweep of unfinished recordings) is reported as lost rather than looped on, since the audio is gone from here too. `utils/recording_api.py` is a pass-through and **stores nothing**: parts are small, so each is held whole in memory for the one request, which is what lets a 401 be answered by refreshing the token and sending it again rather than refreshing before every part. It exists only because the browser holds no token the backend accepts, and lives under `/record`, not `/api`: behind the proxy `/api/*` is scribe-backend's. Answers: 401 wait for sign-in, 409 the backend's own missing list, 422 give up, 404/5xx/network back off (2 s → 60 s, jittered; the attempt count lives in the sync state because `kick()` clears the timer). `owner` (an HMAC of the username under `STORAGE_SECRET`) is derived from the session on every request and never taken from it; the same key tags recordings in IndexedDB so a shared computer does not show one user's recordings to the next — a courtesy, not a control. The routes require the `X-Scribe-Recording: 1` header (CSRF, on top of the SameSite=Lax session cookie). Nothing is ever deleted because a send failed.
- **The original is downloaded from My files, not from the browser or the recorder.** The backend keeps `<job>.orig.enc`, encrypted for the user, for the job's own 7 days. `GET /record/original/<job>` streams it through with the session's decrypted encryption password (not `storage_decrypt()`, which navigates on failure and a download has no page). `jobs_get()` sets `is_recording` from the backend's `has_original`; My files marks those rows with a "Recording" badge (`.jobs-recording-badge`, held at the right edge of the filename cell by `.jobs-filename` so every row's badge lines up). **There is no per-row download: the original is part of Export**, transcribed or not. Every export dialog offers it as an unticked "Include the original recording(s)" option (`show_export_dialog(originals=…)`, `utils/srt_export.py`): the editor's own for the open job when `editor.has_original` (asked of `GET /api/v1/transcriber?job_id=` by `job_has_original()` once `/srt` is up), the bulk one for every recording in the selection. A selection is either all transcribed (one type) or not transcribed at all — **transcribed and untranscribed files are never exported together**, Export is disabled for such a selection and `table_bulk_export()` refuses it. One with recordings and nothing transcribed opens `show_originals_dialog()` instead. Bulk export uses the same wide dialog with a preview (of the first file) as the editor's, subtitles included. **An export of more than one file is always one ZIP**, originals included (`utils/export_zip.py`): the dialog registers what goes in with `prepare_zip()` and gets a single-use, owner-bound link (`/record/export/<token>`, 10 minutes); the route writes the ZIP as it streams — built files first, then each original piped from the backend into its entry chunk by chunk (decrypted there with the session's password, as the single download is), so no original is ever held here whole or written to disk. An original that cannot be had becomes a line in `NOT INCLUDED.txt` inside the ZIP rather than a failed download. A single file still downloads as itself (`/record/original/<uuid>` for one original). **The recorder lists only recordings that have not reached My files** (`others` filters out `state === "uploaded"`); one that just did is announced once in the status line and leaves the list. Nothing plays back on the recorder page.
- **Not being logged out mid-recording**: `page_init(on_session_end=…)` calls the page instead of navigating to logout; `/record` shows a banner and keeps recording.
- Stop and Delete ask twice (a second press within 4 s). Wake Lock keeps a phone's screen on; `beforeunload` asks before leaving a live recording; a hidden page flushes with `requestData()`; a muted track (screen locked on iOS) and time spent in the background are said in words. Capture turns echo cancellation and noise suppression **off** and gain control on — nothing plays back, and suppression cuts quiet distant speech along with the ventilation. 64 kbit/s (`BITRATE`), ~29 MB an hour.
- **A recording whose browser lost track of it can still be finished** ("Unfinished recordings on Scribe" on `/record`). Wiping site data deletes the recording's record, and the record is the only place its id lives -- the parts already sent sat orphaned on the backend until its 7-day sweep. The engine now asks `GET /record/api/unfinished` (→ backend `GET /recordings`) at `init()` and offers whatever the backend holds that this browser has no record of (`refreshOnScribe()`, `onScribe()`), with Finish (`finishOnScribe()`, `POST …/finish` with `{parts}` only) and Delete (`discardOnScribe()`). The route is registered **ahead of `/{rid}`**, which would otherwise take "unfinished" for an id. What it recovers is only what reached Scribe, up to the first gap: audio that was only on the recording device is gone with its storage. It is named "Recovered recording" and typed from `?type=`, which every part now carries (`partPath()`) -- the reader's own name is encrypted on the device that recorded it and is never sent. **The backend lists a recording only once nothing has been sent to it for `RECORDING_RECOVER_AFTER_MINUTES` (10)**: a live recording's id is 128 random bits known to nothing else, and keeping it out of the list is what stops a stolen or second session from finishing or deleting a recording still going; a "this is the live tab" flag would be forgeable by the same session. The other half of that: **`done` carries the part count**, and a recording tab that holds more than the job it became (finished from the list while its phone recorded on offline) raises `finishedElsewhere()` instead of treating `done` as uploaded -- the audio stays on the device, with the error said in words; the backend likewise answers a late part or a larger finish with 422 `already finished` rather than "ok", which the engine would have taken as leave to delete it. Covered in `tests/js/recorder_engine.test.js` and `tests/test_recording.py`.
- **A recording that is already a job is deleted from My files**, like any other file — the recorder has no delete for it (the `/record/api/recent` and `/record/api/job/<uuid>` routes are gone).
- The help text is deliberately device-neutral: a phone is not needed, any up-to-date browser on a computer works the same way.
- **Test audio** (beside "How recording works") opens a dialog to hear the chosen source before a lecture: the same Audio source picker (same setting, remembered the same way), the level history drawn by the main meter's own `drawLevels()`, a level bar in dB (−60…0, RMS with a peak marker, `role="meter"`), and a verdict in words read from the last 1.5 s rather than the instant (`TEST_WINDOW`, since speech has gaps): clipping, almost nothing heard, quiet, or good. It opens its own stream with the same `CAPTURE` constraints the engine records with, so what it hears is what a recording would. "Record 5 seconds and listen" keeps a sample in memory as a blob URL for the browser's own `<audio>` player; closing the dialog (`@hide` → `closeTest()`) stops the microphone and revokes the URL. The test never touches the engine, storage or the network — `test_the_audio_test_keeps_and_sends_nothing` holds it to that. The dB bar and verdict are one local component, `LevelMeter` (with `levelVerdict()`), used by the dialog and by the recording itself under its meter — so both read the same way; while recording the verdict looks back 3 s (`LIVE_WINDOW`) rather than 1.5 s, so a speaker pausing for breath is not told the microphone has gone, and says "Paused." when paused. While recording the verdict is not shown in words (`:words="false"`) — only the bar, coloured by it; the sentence is Test audio's alone. Both are fed from float time-domain samples (`Session.loudness()` in the engine): bytes have nothing below about −42 dB, which is where "is anything heard at all" is decided.
- Tests: `tests/test_recording.py` (the pass-through routes against a mock backend — sent as received, never written to disk, refresh-and-resend on 401, status codes, the store key — and page guards) and `tests/js/recorder_engine.test.js` (node, run from the pytest file when `node` exists) for the engine — no audio written while online, the name never in the clear, spilling on a failed send and going back to memory once caught up, a crash online costing only the unsent part, finish on Stop, offline buildup and drain, lost answers, a part lost on the backend, crash recovery, other users, storage failure, interruptions. `recorder_engine.js` is a static file loaded with its content hash in the URL (`engine_script()`), **served at `/record/recorder_engine.js`, not under `/static`**: behind the reverse proxy `/record` has to reach this app anyway, while nothing guarantees `/static` does — the engine was the only file on the site with a `/static` URL, and on staging that URL was answered 404 by something else ("The recorder did not load"); `recorder.js`/`recorder_reminder.js` have the usual component-registration gotcha.

## Sunet Drive (`utils/drive.py`, `utils/drive_dialogs.py`)

Get from / Save to Sunet Drive, [SUNET/scribe-backend#64](https://github.com/SUNET/scribe-backend/issues/64). Sunet Drive is Nextcloud, one instance per organisation (`https://<org>.drive.sunet.se`; `drive.sunet.se` itself is only a discovery front door). The backend does all of the talking to Drive -- this repo only calls `/api/v1/drive/*` -- and files move **server to server**, never through the reader's device.

- **Offered and configured per organisation only.** A customer has `drive_enabled`, its `drive_url` (required when enabled -- `drive_fields_valid()` says so on the field, and the backend refuses it too) and an optional `drive_display_name` (admin customer pages, `drive_fields()`). Readers do **not** choose an instance: that was tried in User settings and taken out, and an organisation without an instance simply does not get Drive. The backend accepts only https hosts under `DRIVE_ALLOWED_HOST_SUFFIXES` (default `.drive.sunet.se`). Nothing about Drive is drawn when the organisation does not offer it: every entry point asks `drive_status()` first and stays hidden otherwise.
- **User settings only says whether the reader is signed in, and logs them out** (`draw_drive_section()` in `pages/user.py`, "Log out from {name}" -> `drive_logout()`), which revokes Scribe's access in Drive too. Nothing to configure there.
- **The name is the organisation's.** The My files button reads "From {name}" (the dialog it opens is titled "Import from {name}"), the export one "Save to {name}", via `display_name()`, falling back to "Sunet Drive". Presentation only.
- **Connecting is a visible step out of Scribe** (`ensure_connected()`): Nextcloud Login Flow v2. The reader opens their Drive in a tab of its own, signs in and grants access there; the dialog polls until the grant arrives. The link is a real `<a target="_blank">` the reader clicks, not a server-side `window.open` -- the login URL only exists after a round trip, and a window opened then is no longer part of the click, so popup blockers stop it. Scribe never sees a Drive password; the backend holds the app password Drive issues, encrypted, for an idle hour, and revokes it in Drive when it expires or the reader logs out.
- **The browser is Scribe's own** (`DriveBrowser`): Nextcloud has no picker an outside site can embed. File mode picks **several files** -- up to `MAX_FILES`, from any number of folders; `selected` is kept while the reader moves between folders, "Select all here" takes the current folder's media -- and offers only the formats the upload dialog accepts (the backend marks each entry `media`). Each file row is a `<label>` (`tag="label"`) around a real checkbox, so the whole row toggles it and a screen reader meets a named checkbox. `get_from_drive()` then imports them one at a time -- each its own job, `on_imported()` after each so they appear as they land; one failure does not stop the rest, a lost connection does. **Cancel is always there and stops at once**, mid-file too, one file or many: each import runs as a task (`background_tasks.create`, `handle_exceptions=False`, since its outcome is awaited right there) and Cancel cancels it, which closes the request -- the backend notices the dropped connection, abandons the transfer and removes the half-made job. Files already imported stay. Folder mode picks where to save and, for one file, its name. An existing file is never overwritten silently -- `save_to_drive()` asks Replace / Keep both / Skip.
- **Export builds one list for both destinations.** `exp()` in `srt_export.py` produces `(name, bytes)` pairs once; a download of more than one file (originals counted) is one streamed ZIP, Drive takes each as its own file. When "Include the original recording" is ticked, Save to Drive saves the originals too (`save_to_drive(files, originals)`), and the originals-only export dialog has its own Save to Drive button. An original is sent **by job id**: `drive_save_original()` hands the backend the reader's encryption password, the backend decrypts the original and streams it straight into Drive, so it never passes through this process. That originals-only dialog stays open until the save is done -- the Drive dialogs open from inside it, and Quasar does not draw a closed dialog's contents. `exp` takes `to_drive`, so the dialog's Download button must stay `on_click=lambda: exp()` -- handed `exp` directly, NiceGUI passes the click event as `to_drive` and every download goes to Drive.
- **Reasons, not status codes.** Every call answers a `DriveResult`; the dialogs act on `reason` (`not_connected` -> connect again, `exists` -> ask). The backend answers a lost Drive grant with 409, not 401, since a 401 from the API means the *Scribe* session is over.

Covered by `tests/test_drive.py` (this repo) and `tests/test_drive.py` in scribe-backend.

## Information dialog (`pages/srt.py`)

What is open and what is in it — file name, language, caption count, reading speed — behind an **Info** button in the toolbar rather than laid across it: it is read when a reader wonders, not while they work, and a dialog has room to say what each figure means instead of leaving a row of bare numbers to a tooltip.

The two moving figures (`captions`, `wpm`) are labels registered by name through `SRTEditor.set_status_elements(**labels)`, and `update_status()` redraws them — it fills only what the page registered, so `status_values()` still answers `duration` (and `format_duration()` still gives `m:ss`/`h:mm:ss`) for any caller that wants it. The dialog does not: a running time taken from the last caption's end says where the subtitles stop, not how long the recording is, which is what a row called "Length" is read as. The count is worded for the format — captions or paragraphs, in both the row label and the figure itself, never "block" — and that word is the *only* thing the two formats' rows differ in: one set of rows, naming the recording "Media file" and explaining each figure in terms of the transcription it came from, with `counted` ("captions"/"paragraphs") standing in for the block noun. Each row is a small bold heading with its value under it and an italic sentence saying what the value means (`.editor-info-row` is a column, not the two-column form it was: a fixed 8rem label column left the filename, the one value with no room to spare, whatever was left). **`renumber_captions()` is what calls `update_status()`** — it runs after parsing and after every structural edit, which is the only hook that always fires; registering the labels happens while the toolbar is built, long before the captions are parsed, so without it the dialog reported an empty editor for the whole session. The file name and the language never change, so they are drawn once.

## Keeping a session (and unsaved edits) alive

The captions being edited live in that client's own `SRTEditor` **on the server**. Anything that reloads the page or ends the session throws them away back to the last save, so three separate reload paths are deliberately handled:

- **`@ui.page("/srt", reconnect_timeout=300)`** (`pages/srt.py`). The default is 15s (`main.py`), which also sets the socket ping (`ping_interval` 12s, `ping_timeout` 6s) — so ~18s of stalled connection ends it. Past the timeout NiceGUI **deletes the client's content** (`nicegui/client.py`) and the browser reloads itself on return (`nicegui.js`, "reloading because handshake failed"). A closed laptop lid, a wifi hop or an idle proxy was enough. Other pages keep the short default: nothing unsaved lives on them.
- **Refreshing distinguishes "refused" from "could not ask"** (`utils/token.py`). `token_refresh_call()` returns `None` only for a 4xx — that session is genuinely over — and raises `RefreshUnavailable` for a network error, a 5xx or an answer with no token. `token_refresh_or_wait()` turns that into "keep the session" until `MAX_REFRESH_FAILURES` in a row (10 × the 30s timer in `page_init` ≈ five minutes of an unreachable provider). Before this, `except (httpx.HTTPError, Exception): return None` meant one blip logged the reader out mid-edit.
- **The OS-theme reload is only for chart pages.** `reload_on_theme_change()` exists because Plotly is drawn server-side in one theme's colours and cannot restyle itself; it is called by `analytics.py`, `groups.py` and `health.py` rather than by `page_init`, which used to install it on every page — including the editor, where a Mac switching to dark at sunset reloaded the captions away. Everything else follows the theme through CSS custom properties. (The manual dark-mode button further down `page_init` still reloads, and already skips `/srt` for the same reason.)

`tests/test_session.py` covers all three. What none of them covers is a browser crash or a closed tab — that needs a local draft, which does not exist yet for the editor (the recorder has one; see "Recording").

## Settings

`utils/settings.py` `Settings` (pydantic `BaseSettings`, loaded from `.env`):

Access via `get_settings()` (cached).

## Admin hierarchy

- **BOFH** (`bofh=True`): sees everything, manages all realms and onboarding attributes
- **Realm Admin** (`admin=True`): scoped to own realm + `admin_domains`. Can manage rules for their realms
- **Regular User**: no admin access

## Onboarding rules (pages/admin/rules.py)

- Rules page at `/admin/rules` — table with create/edit/delete dialogs and per-row test/delete actions
- Realm field is a multi-select dropdown filtered to real domains (containing a dot/TLD)
- Rules scoped by realm — admins within the same organisation see the same rules
- BOFH users see all rules across all realms
- Onboarding attributes section hidden for non-BOFH users
- Help dialog explains rule matching, actions, scoping, and manual override
- "Attributes" terminology used throughout (not "JWT claims")
